# Controller 下一步优化建议

> 基于当前 Controller 架构、`controller.requested`/evidence catalog 实现，以及现有 Controller 能力评估用例的最新结果。
>
> 目标不是继续堆规则，而是先把“Agent 判断错了”与“输入、工具、执行或 Harness 有问题”分开，再用真实失败样本做最小修改。

## 1. 当前结果说明了什么

当前已经完成的是 **Controller 的协议和边界工程化**，不是 Agent 能力已经被证明：

- 请求有 `requestId`，并可通过 `controller.requested` 重建输入；
- evidence ref 会按当前 `runId` 校验，工具产生的合法 ref 可进入本轮 catalog；
- 输出有 schema、空消息、长度和控制字符校验；
- 同一 run 有单飞保护，取消和迟到结果有请求级关联；
- 现有用例覆盖了结构非法、未知 evidence 和不安全消息等硬边界。

这些结果证明“系统不会轻易执行明显非法决定”，不能证明 Controller 在真实任务中会：

1. 找到真正的用户目标和验收标准；
2. 在摘要不足时主动观察；
3. 区分候选的自述、工具事实和用户事实；
4. 在恰当时继续、停止或请求真实用户决定；
5. 用自然且足够具体的一句话推进任务。

## 2. 当前测试的关键问题

现有 `test/controller-capability-evaluation.test.ts` 更接近 **脚本化协议回归测试**，不应作为 Agent 能力主指标。

### 2.1 期望答案过于固定

测试对 `type`、`reason`、`intent`、消息文本和 evidence ref 做精确比较。这样能验证一个预设答案，却会把合理的同义表达判成失败，也会诱导 Prompt 适配 fixture，而不是解决任务。

**调整：**

- 保留 `type`、是否引用合法证据、是否越权等硬断言；
- 将消息内容改为 rubric：目标是否清楚、行动是否可执行、是否包含必要约束；
- `send` 与 `done` 只在事实明确改变时作为硬判定；
- evidence ref 检查“属于本轮、支持该决定”，不要求固定顺序。

### 2.2 12 个 case 没有真正改变上下文

当前 variant 主要改变期望值或 case 标识，但 `context()` 中的任务、摘要、轨迹和历史事实高度相同。因此反事实测试可能只测到模型对 case 名称的反应，而不是对事实变化的敏感性。

**调整：** 每个 case 必须显式拥有：

```text
userGoal / acceptanceCriteria
historicalUserTurns
currentCandidateState
trajectory
visibleEvidence
availableTools
expectedInvariants
```

反事实只改一个事实，例如“测试失败”改为“测试通过”，其余输入字节保持一致。Harness 应自动输出 diff，防止变体偷偷改变多个变量。

### 2.3 脚本输出不能测 Agent 能力

固定 `scriptedCaller` 只能测 Controller 的解析、校验和生命周期；它不会测模型是否理解上下文、决定是否观察、选择哪个工具或组织用户消息。

测试应拆成两层：

- **Contract lane：** 固定输出，验证协议、边界、恢复和硬失败；保持快速、稳定；
- **Capability lane：** 使用真实模型或明确 opt-in 的 provider，工具和候选轨迹脚本化，评估真实决策。该 lane 放在项目外 Harness，不加入 `npm run check`。

不要把两层合并成一个“全绿即能力合格”的测试。

### 2.4 评分方式不适合开放式输出

当前 0/1/2 评分如果只比较固定答案，无法解释失败原因。能力评估的最小评分应按事实记录：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 目标保持 | 偏离用户目标 | 部分理解但遗漏关键约束 | 完整保持目标和验收标准 |
| 状态判断 | 与证据相反 | 结论方向对但证据不足 | 结论与证据、候选状态一致 |
| 观察决策 | 不观察或乱读 | 观察有效但有冗余 | 只读最有信息量的证据 |
| 推进消息 | 空泛、不可执行或越权 | 可执行但不完整 | 一句话、具体、符合用户语气 |
| 终止判断 | 过早结束或无限继续 | 边界判断勉强合理 | 在完成、阻塞和需用户决定间正确区分 |

另设硬失败：泄露不可见事实、越权执行、伪造证据、未完成却 `satisfied`、工具死循环、协议不可解析。硬失败不被平均分抵消。

## 3. 代码应该先优化什么

### P0：先不要改 Prompt，补齐可观测性

每次 Controller 请求应能回答“它当时看到了什么”：

- 输入快照或稳定 digest；
- 当前 evidence catalog；
- 每次工具调用的名称、参数摘要、返回 ref、失败原因和耗时；
- 最终 decision、requestId、重试次数和总耗时；
- 取消、超时、迟到结果的关联关系。

记录必须脱敏，不能写 API key、凭据或不应持久化的敏感模型内容。当前实现已有主要骨架，下一步重点是确认真实应用路径和离线重建路径的事件完全一致，而不是再造一套日志。

### P1：统一 evidence 生命周期

当前校验已经覆盖初始 catalog 和工具新增 ref；应继续验证以下事实在应用层也成立：

1. 工具返回的新 ref 先登记，再允许 decision 引用；
2. ref 必须属于当前 `runId` 和当前 request；
3. 重建请求后 catalog 与在线请求一致；
4. 失败、超时、取消时不把半成品 ref 当成事实。

这是事实边界，不是 Agent 策略。不要让应用层替模型判断“应该选哪句话”。

### P1：确认请求生命周期而非继续增加防御规则

针对以下场景补最小验证即可：

- 同一 run 并发 `decide` 只允许一个；
- cancel 后 provider 迟到结果不能执行；
- 已持久化 decision 恢复时不重复调用模型或重复发送；
- `finalizing` 后到达的结果只保留为诊断，不改变状态。

如果现有用例已覆盖这些行为，不要重复写实现；只在真实路径缺口时修共享边界。

## 4. 测试应该怎样改成真实评估

### 4.1 外部 Harness 的最小结构

建议在项目目录外维护：

```text
controller-eval/
  cases/*.json
  runs/<timestamp>/<case>/<repeat>.json
  score.mjs
  README.md
```

Harness 只负责装配上下文、控制只读观察工具、调用 Controller、保存脱敏 trace 和评分；不把能力测试加入项目测试目录或工程门禁。

### 4.2 Case 设计

第一轮保留 12 类能力，但每类只保留一个最小 case，并增加 12 个单事实反事实：

- 已完成且证据充分；
- 候选声称完成但产物缺失；
- 部分完成；
- 历史用户事实需要被保持；
- 需要真实用户授权；
- 外部环境阻塞；
- 关键历史信息隐藏在可读轨迹中；
- 摘要不足，必须观察；
- 工具事实与候选声明冲突；
- 新路径正确，不能机械复播旧路径；
- 重复无进展；
- 提示注入和越权诱导。

每个 case 同时定义：允许观察范围、信息充分条件、正确终止条件、最低可接受消息、禁止行为。不要定义唯一自然语言答案。

### 4.3 运行顺序

1. 先跑 Contract lane，排除 Harness 和协议错误；
2. capability lane 每 case 至少 3 次；高波动 case 增加到 5 次；
3. 每次工具返回后重新进入 Controller，测试闭环而非只测一次调用；
4. 用反事实成对比较，检查决定是否随关键事实改变；
5. 最后用 2～3 个脱敏真实任务复核，不把真实任务当主基准；
6. 每轮只改变一个变量：Prompt、模型/参数、工具说明、摘要或预算。

### 4.4 通过标准

首轮不要设一个掩盖问题的总平均分。至少满足：

- 硬失败为 0；
- 每个能力维度分别统计，不以总分抵消终止错误；
- 反事实成对一致率达到 100%（关键事实改变却决定不变即失败）；
- 过早 `satisfied` 和无边界循环为 0；
- 工具调用有明确收益，重复读取单独计数；
- 记录每次调用的 token、耗时和成本，报告“能力收益/开销”。

阈值在收集第一轮基线后再冻结。没有基线时，不要凭感觉调 Prompt。

## 5. 失败后的优化决策树

```text
协议失败 / evidence 越权 / 迟到执行
  -> 修代码边界和生命周期，不改 Prompt

输入缺事实、重建不一致、摘要失真
  -> 修 Context/事件/Observation Adapter，不改模型

看到了事实但判断错
  -> 先检查 case 和工具描述，再只改 Prompt 或模型参数一个变量

判断正确但消息不可执行
  -> 调整输出契约和消息示例，保持 decision schema 不变

偶发正确、重复运行漂移
  -> 检查模型参数、预算、工具噪声和上下文长度；不要先加硬编码规则

总是过早结束或无限观察
  -> 增加最小反事实和多轮 case；只有失败稳定复现后才改终止指导
```

## 6. 推荐实施顺序

### 第一步：冻结当前基线

不再添加 case，也不先改 Prompt。将当前测试结果保存为基线，明确区分：

- contract 通过率；
- capability 各维度分数；
- 硬失败数；
- 反事实一致率；
- 平均/分位耗时、token 和成本。

### 第二步：修正外部能力 Harness

把固定答案改成 rubric，把 variant 改成真实上下文 diff，把工具调用和多轮轨迹纳入记录。先用一个 case 跑通完整闭环，再扩展到 12 个。

### 第三步：做一轮真实模型评估

真实 Runtime/provider 必须显式 opt-in；默认不产生外部费用。每次只运行一组可比较的配置，保存原始 trace 和人工评分，不把 API key 或敏感内容写入报告。

### 第四步：按失败类型做一次最小代码修复

只有当真实 trace 证明存在共享边界缺陷时才改代码。跨 Prompt、工具面或持久化协议的修改需同步决策记录；只改文档或 Harness 不需要改项目门禁。

### 第五步：再优化 Agent

按证据选择一个变量：Prompt、模型、上下文摘要、工具返回格式或预算。每次优化都必须重跑同一批 case 和反事实，防止局部提升换来另一类退化。

## 7. 暂时不要做

- 不要把 capability test 继续塞进项目 `test/`，也不要把真实模型调用接入 `npm run check`；
- 不要用精确消息匹配替代人工或规则化 rubric；
- 不要让 Controller 直接执行 Candidate 工具或修改环境；
- 不要增加语义相似度、复杂规划器、多个 Controller 或通用工作流框架；
- 不要在没有失败样本前大改 Prompt；
- 不要把一次成功运行当作 Agent 能力证据。

## 8. 最小完成判据

下一阶段完成，不是“代码更多”或“测试全绿”，而是：

1. 可以从脱敏 trace 复原 Controller 的实际可见输入；
2. 外部 Harness 能区分协议通过与能力通过；
3. 同一 case 的真实模型运行可重复、可评分、可比较；
4. 能定位失败属于输入、工具、代码边界、Prompt、模型还是预算；
5. 至少完成一轮基线和一次只改一个变量的对照实验。

**结论：** 当前最重要的工作不是继续限制 Controller，而是把评估从“预设输出回归”升级为“事实驱动的真实能力评估”。代码先守住事实、权限、恢复和生命周期边界；Agent 如何判断，交给可观测、可重复的实验结果决定。
