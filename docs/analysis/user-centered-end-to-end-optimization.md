# Reprise 全流程分析与核心优化建议

状态：基于当前工作区实现的产品审视
日期：2026-08-13

## 1. 先说结论

Reprise 的核心不是“运行三个内部 Agent”，也不是“保存完整 trace”，而是帮助用户以尽可能低的认知成本回答一个私人决策：

> 对我做过的这类真实任务，换成候选模型后，我是否更愿意使用它？

当前项目已经有一条可信的技术纵切片：历史会话可冻结，候选在隔离目录运行，Controller 可续接交互，事实可持久化，Comparison 可生成报告，失败不会伪造结论。安全与审计底座是项目目前最扎实的部分。

但从用户视角看，产品闭环仍不完整。主要矛盾不是能力不足，而是**核心决策被配置、内部术语和技术事实淹没**：用户难以开始一次实验，也难以在结束后快速回答“是否值得换模型”。

因此下一阶段不应扩展 Agent、插件、指标或页面，而应只做两件事：

1. 把启动实验压缩成一条有默认值、可回退的引导路径；
2. 把运行结果压缩成一张可判断、可追证的对比结论页。

## 2. 第一性原理

### 2.1 用户真正需要完成的动作

从最终决策反推，用户只需要提供三项不可推断的信息：

1. **比较哪次任务**：选择一段历史会话；
2. **比较哪个模型**：选择目标 Runtime 可验证的候选模型；
3. **是否接受本次比较限制与成本**：确认后开始。

其他信息只要系统能够从历史会话、当前 Runtime、环境和本地配置中可靠推断，就不应再次要求用户输入。

### 2.2 一个结果何时有用

结果至少同时满足四个条件才有决策价值：

- **任务相同**：历史任务与候选任务边界一致；
- **条件可解释**：环境、Runtime、模型解析和外部世界差异明确；
- **结果可核对**：用户能看到回复、改动、验证和关键证据；
- **代价可比较**：至少知道耗时、调用量、token/成本可用性和人工追加输入。

缺少任一项时，系统应降低结论强度，而不是用更多内部日志补偿。

### 2.3 应删除的认知负担

对用户而言，`TaskCase`、`CandidateRun`、`Recovery`、`Controller`、`Comparison`、`fidelity`、`artifact ref` 和 `Host fact` 都是实现细节。它们可以保留在领域模型与审计层，但主流程只应使用：

- 历史任务；
- 候选模型；
- 运行条件；
- 运行过程；
- 比较结果；
- 限制与证据。

## 3. 当前全流程

```text
启动 TUI
→ 配置 Harness 内部模型
→ 浏览 Codex 历史会话
→ 检查并冻结 TaskCase
→ 再次发起 /run
→ 手工输入 source root
→ Runtime 与环境 preflight
→ 必要时确认 observational 限制
→ 启动隔离候选运行
→ Recovery 恢复环境
→ Candidate 执行任务
→ Controller 判断是否追加输入或结束
→ 捕获工作区变化、trace 与 RunRecord
→ Comparison 读取证据并写 comparison.md
→ 生成 HTML 报告
→ TUI 显示技术摘要
→ 用户到 /history 或文件路径继续查看
```

### 3.1 已经做对的部分

- **历史基线不重放**：直接使用原始完成结果，避免把“复现历史模型”变成另一个不可控实验。
- **候选运行隔离**：不修改原工作区和全局 Codex 配置，风险边界正确。
- **目标 Runtime 验证模型**：候选不是由 Harness 模型目录推断，变量定义正确。
- **内部 Agent 职责分离**：Recovery、Controller、Comparison 不共享领域职责，失败也不会伪造领域结果。
- **事实先持久化、界面后投影**：TUI 退出或渲染失败不会改变运行事实。
- **Comparison 无叙事时安全降级**：仍可展示 Host facts，不虚构结论。
- **隐私与凭据边界明确**：配置保存引用而非密钥值，历史文本是否发给模型由用户控制。

这些能力应保留，但不再继续横向扩展，除非真实用户流程暴露新的阻断或误导。

## 4. 核心问题

### P0：实验入口不是一条连续路径

当前主流程被拆成 `/config`、`/intake`、`/run`、`/history` 四个用户需要记忆和编排的命令。冻结历史会话后回到 Home，运行前还要再次输入 `/run`；运行结束后回到 Home 或历史页寻找报告。

这与用户心智不一致。用户不是来“管理工作台模块”，而是来“做一次比较”。

**影响**：首次使用容易停住；用户必须理解系统状态和命令关系；流程是否完成依赖记忆，而不是界面引导。

### P0：系统已知道历史工作区，却要求用户重新输入 source root

会话导入已经解析并保存 `cwd`/`historicalCwd`，但 `/run` 仍要求用户手工输入绝对源目录。这个输入既高摩擦又高风险：输入错误目录会让实验退化为 observational，用户还可能不理解为何比较条件变差。

**影响**：最关键的实验条件依赖重复输入，且错误会直接降低结论可信度。

### P0：候选模型写死，用户没有完成核心选择

生产 TUI bridge 当前把候选固定为 `gpt-5.6-luna`，reasoning 固定展示为 high。用户既不能从目标 Runtime 的可验证模型中选择，也不能清楚区分“内部 Harness 模型”和“被测候选模型”。

**影响**：产品定义中的核心变量并未真正交给用户；当前更接近单一验证脚本，而不是个人模型决策工具。

### P0：结果页回答的是“系统发生了什么”，不是“候选是否值得使用”

当前 TUI 结果只显示 run id、termination、cleanup、fidelity、Controller/Comparison/Recovery 状态和报告路径。HTML 报告主要展示任务、Comparison 链接、运行技术字段和 artifact 列表，也没有默认并排呈现：

- 原结果与候选结果；
- 文件改动摘要；
- 验证/测试结果；
- 耗时、token、成本和调用次数；
- Controller 追加了什么输入；
- 哪些差异足以影响用户选择。

**影响**：用户完成了昂贵实验，却仍需阅读 `comparison.md`、trace 和 artifact，自行拼装结论。核心价值停在数据采集层，没有完成决策交付。

### P1：首次配置是内部系统表单，不是完成任务的最小设置

已有真实反馈表明 `/config` 难用。当前页面同时暴露 provider type、provider label、base URL、model、effort、key reference，并要求用户理解 Enter、方向键、`s`、`t`、Esc 的状态差异。

**影响**：用户在尚未看到产品价值前，先承担最复杂的交互和内部概念学习。

### P1：环境恢复的严格度被数据模型预先限制

冻结 Codex 会话时，环境基线只有 `partial/unavailable`，没有冻结当时工作区 fingerprint；严格比较只有在 TaskCase 已有可核对 fingerprint 时才成立。对普通历史会话而言，系统大概率只能给 observational 结论。

这不是实现错误，而是客观证据边界。但当前体验容易让用户误以为“选择原目录”就等于恢复了历史起点。

**影响**：比较可信度可能被高估。若不在结果首屏明确解释，这是误导风险，而不只是技术限制。

### P1：价值指标只存在于契约或愿景中，尚未形成稳定事实

Schema 有 token/cost budget，Runtime capability 也声明 token telemetry，但当前主要投影只展示 trace 序号范围；报告没有稳定呈现耗时、token、成本、调用次数和人工输入次数。

**影响**：即使候选质量相近，用户也无法比较效率和使用成本；产品问题中的“结果、效率和成本”只完成了第一项的一部分。

### P2：界面语言过度暴露架构

例如 `Harness agents`、`Recovery`、`Controller`、`Comparison`、`fidelity observational`、`TaskCase`、`runtime resolved` 等词直接进入主页面。

**影响**：开发者可以理解，普通用户需要先学习架构才能判断一次实验。技术状态应该可展开，而不是成为摘要主体。

### P2：TUI 单文件已逼近维护上限

`src/tui/codex-intake.ts` 接近 1000 行，同时负责页面状态、键盘路由、配置编辑、会话导入、历史、运行、时间线和渲染。它尚未超过项目限制，但继续加候选选择和结果页会快速恶化。

**影响**：后续每个用户体验修改都会触碰同一状态机，增加回归风险。这里需要的是按现有页面职责做最小拆分，不是引入新 UI 框架或通用状态管理器。

## 5. 优化建议

### 建议一：建立唯一主路径“新建比较”

Home 首屏只保留一个主动作：

```text
新建比较
→ 选择历史任务
→ 选择候选模型
→ 检查运行条件
→ 开始
→ 查看结果
```

`配置` 和 `历史` 作为次级入口存在；缺少配置时，在主路径中就地完成一次最小设置。冻结会话后直接进入候选选择，不再返回 Home 等待用户输入 `/run`。

**最小改法**：复用现有 pages 和 handlers，仅增加一个顺序推进的入口与默认 next action；不要引入新的 workflow engine。

**完成判据**：新用户不看 `/help`，也能从启动走到开始实验。

### 建议二：自动带入历史工作区，只在异常时让用户修正

优先级如下：

1. 使用 TaskCase 的 `historicalCwd`；
2. 若目录存在，直接作为默认 source root 并执行只读 preflight；
3. 若目录不存在或不安全，再提示选择/输入目录；
4. 在确认页显示“历史路径、当前路径、是否匹配”，而不是只显示抽象 fidelity。

**最小改法**：已有 `taskContext.historicalCwd` 和路径校验可复用，不需要新的目录发现系统。

**完成判据**：正常本机历史会话无需手工输入路径；错误目录不能在无清晰提示下继续。

### 建议三：把候选模型选择补成真正的核心步骤

候选必须来自目标 Codex Runtime 的发现或验证结果。界面只显示：

```text
被测模型
❯ gpt-x   已验证
  gpt-y   已验证
  手工输入模型标识…
```

内部 Harness 模型放在“高级设置”，默认沿用已保存配置，不与被测模型并列展示。reasoning effort 若属于候选条件，也应作为候选设置的一部分显式记录，而不是写死在文案中。

**最小改法**：复用 `RuntimePort.resolve/validateCandidate`；不建设通用模型注册表，不接入 Pi 候选列表。

**完成判据**：运行前用户能用一句话回答“我正在用哪个候选模型，与哪个历史结果比较”。

### 建议四：重做结果首屏，按用户判断顺序投影已有事实

结果页固定按以下顺序展示：

1. **一句话状态**：可比较 / 仅供参考 / 无法比较；
2. **原结果 vs 候选结果**：最终可见回复和关键产物并排或顺序对照；
3. **候选做了什么**：文件新增、修改、删除，验证命令与结果；
4. **协作差异**：Controller 追加输入次数和文本；
5. **效率事实**：耗时、target/controller/comparison 调用、token、成本；不可用就明确写“未获取”，不要省略；
6. **限制**：用自然语言说明环境、外部世界和模型解析差异；
7. **证据入口**：报告、diff、trace 和 artifact。

Comparison 负责组织观察，不负责宣布统一赢家。Host facts 始终独立显示。

**最小改法**：先扩展现有 `ComparisonProjection` 与 `renderResult`，复用已经持久化的 RunRecord、事件和 workspace scope artifact；不要创建第二套结果模型或 Web 应用。

**完成判据**：用户只看结果首屏即可形成初步判断，需要核实时才打开详情。

### 建议五：把配置缩成“连接方式”，默认隐藏内部字段

首次配置只问必需项：

```text
API 地址
模型
密钥环境变量名
[测试并保存]
```

provider label 自动生成；provider type 由是否自定义 endpoint 推断；effort 使用默认值并放入高级项；“测试”和“保存”合并为一个明确动作，但在按钮旁说明会发送最小请求。已有配置时主流程不再打断用户。

如果短期不重做 TUI 表单，最克制的过渡方案是提供一条受校验的 CLI setup 命令，并在 TUI 中显示可复制命令，而不是继续扩展复杂键盘编辑器。

**完成判据**：用户无需理解 Pi、provider label 或 key reference 语法即可完成配置，密钥仍不落盘。

### 建议六：诚实区分“严格比较”和“参考性重跑”

将技术 fidelity 映射成用户语言：

- **可比较**：历史起点有证据且当前环境匹配；
- **仅供参考**：使用当前目录近似历史起点；
- **无法比较**：源环境不可用或候选模型未验证。

对从历史 rollout 导入、但没有历史 workspace snapshot/fingerprint 的任务，默认显示“仅供参考”，并明确原因：系统知道历史目录，不等于拥有历史起点。

不要为了提高“严格率”建设复杂恢复系统。只有真实用户反复需要严格比较时，再增加一个最小能力：用户在完成任务时主动保存可恢复快照，供未来实验使用。

**完成判据**：用户不会把 observational 结果误读为严格归因于模型差异。

### 建议七：只补决策所需的最小遥测

稳定记录并投影：

- 开始/结束时间与 wall-clock；
- target、controller、comparison 的模型调用次数；
- target 工具/命令次数；
- Controller 发送次数；
- token 与成本：有原生数据则记录，没有则标记 unavailable；
- 取消、失败、cleanup 状态。

不要建立通用 metrics 平台、图表系统或估算成本引擎。原生数据不存在时，明确缺失比猜测更可信。

**完成判据**：用户能比较“更好多少、慢多少、贵多少、需要多少人工协作”。

### 建议八：在增加功能前做一次最小职责拆分

仅拆 `src/tui/codex-intake.ts` 中最稳定、最独立的部分：

- 配置草稿与校验；
- 纯渲染函数；
- 页面状态与键盘流程仍留在主类。

不要引入状态管理依赖、组件框架或通用页面基类。目标只是给候选选择和结果投影腾出可维护空间。

**完成判据**：主 TUI 文件明显低于 1000 行，新流程改动不需要同时修改配置渲染细节。

## 6. 建议实施顺序

### 阶段 A：先闭合用户决策链

1. 自动带入 `historicalCwd`；
2. 增加候选模型选择；
3. 冻结任务后连续进入运行准备；
4. 结果首屏展示原结果、候选结果、改动、验证与限制。

这是最高价值阶段。完成后先做一次真实用户实验，不继续扩展。

### 阶段 B：只修真实阻断

根据真实使用记录，仅处理：

1. 配置是否仍阻断；
2. 结果是否仍需用户手工拼装；
3. 比较等级是否会被误解；
4. 缺失的遥测是否影响模型选择。

### 阶段 C：有重复需求才扩展

只有出现明确、重复的真实需求时，再考虑：

- 主动保存可恢复历史快照；
- Claude Code Product Pack；
- 多候选批量比较。

不做公共排行榜、统一总分、云同步、插件市场、通用 Agent 平台或复杂 dashboard。

## 7. 明确不建议做的事

- 不继续增加 slash 命令；
- 不让用户分别配置 Recovery、Controller、Comparison，除非高级用户明确要求；
- 不为所有任务设计统一质量分数；
- 不用更多 Agent 弥补结果投影不足；
- 不把 trace 数量当作效率指标；
- 不在没有原生数据时估算 token 或成本；
- 不为了“未来多产品”提前建设通用插件框架；
- 不把严格复现不可得的问题包装成技术术语后继续运行。

## 8. 产品级 Done-means

一名不了解 Reprise 架构的新用户可以独立完成：

```text
启动
→ 选择一段历史任务
→ 选择一个已验证候选模型
→ 看懂本次比较条件
→ 一次确认后运行或取消
→ 在结果首屏判断是否愿意换模型
→ 必要时打开证据核对
```

同时满足：

- 无需输入系统已经知道的路径和配置；
- 无需理解 Harness、Recovery、Controller、Comparison、TaskCase 等内部术语；
- 无需从 trace 和 artifact 列表中自行拼装结论；
- 原工作区、全局配置和密钥不被修改；
- 参考性比较不会被表述成严格因果结论。

达到这个闭环后停止开发，等待下一条真实用户反馈。

## 9. 最终优先级摘要

| 优先级 | 事项 | 用户价值 | 建议动作 |
|---|---|---|---|
| P0 | 唯一“新建比较”主路径 | 能顺利完成实验 | 串联现有页面，减少命令记忆 |
| P0 | 自动使用历史工作区 | 降低摩擦与错误 | 默认 `historicalCwd`，异常时修正 |
| P0 | 候选模型可选择且由 Runtime 验证 | 用户真正控制实验变量 | 增加最小选择页 |
| P0 | 决策型结果首屏 | 完成产品价值交付 | 对照结果、改动、验证、代价、限制 |
| P1 | 简化首次配置 | 降低首次流失 | 最小字段或 CLI 过渡 |
| P1 | 诚实表达比较等级 | 避免错误归因 | 用户语言替代 fidelity 术语 |
| P1 | 补最小效率遥测 | 支持质量之外的选择 | 记录原生事实，缺失明确标注 |
| P2 | 最小拆分 TUI 文件 | 控制后续改动风险 | 只提取配置与纯渲染 |
