当前架构基线 · 模块化单体

把真实历史任务，变成可信的个人模型对照实验。

Harness 不重放旧 Agent，也不评价脱离产品的“裸模型能力”。它冻结历史任务，尽量恢复任务开始前环境，再用当前已安装的 Codex / Claude Code Runtime 驱动候选模型；动态 Controller 模拟同等人类协作，最后由 Comparison 整理证据供用户自己判断。

唯一主动变量候选模型；Runtime、环境、Controller 与预算尽量固定并记录偏差。
事实优先历史结果不重跑；输入、turn、工具、产物、停止与清理都可追溯。
本地与隔离候选运行只进入 Harness 自有副本，无法安全隔离就不直接运行。
01 · System boundary

一句话看懂系统边界

它不是新的通用 Agent Loop，而是一个确定性实验应用，把三个相互隔离的智能模块连接到产品适配器、环境与事实存储上。

历史世界

完整会话、第一条可执行输入、历史结果证据、Runtime 来源事实、环境线索。

→

Experiment Application

确定性 Case Preparation + Candidate Run + Comparison Projection。

Recovery恢复语义判断
Controller动态用户协作
Comparison证据组织说明
→

可判断的证据

不可变 TaskCase、每候选 RunRecord、trace、artifact、fidelity、TUI 摘要与本地报告。

最关键的分离：原始完成结果直接作为历史基线，不进入 TargetRunner；只有候选模型运行进入执行平面。Comparison 只比较“每个候选 vs 原始基线”，不做候选之间排名。
02 · Lifecycle

三个阶段，三种不同责任

阶段之间传递冻结对象与只读投影，不共享可变全局状态。

1

Case Preparation

历史会话 → 导入 → 环境恢复与验证 → 冻结 TaskCase

  • Product Pack 解析私有会话
  • Recovery 在 staging 中工作
  • Provider 验证后冻结 EnvironmentBaseline
  • 更改任何证据就创建新 Case
2

Candidate Run

TaskCase + CandidateSpec → 当前 Runtime → 隔离副本 → Controller 循环 → RunRecord

  • 每候选独立 run ID、环境和 trace
  • 只在稳定 settlement 后调用 Controller
  • 所有终止都经过 finalizing
  • 先写 RunAttempt，准备成功后才写含 Runtime/模型的 RunManifest
3

Comparison Projection

BaselineEvidence + RunRecord → ComparisonResult → Renderer

  • 只读，不改变运行结果
  • Agent 选择值得看的差异
  • Renderer 确定性校验证据引用
  • 失败可降级，不回写 CandidateRun
03 · Modules

每个模块拥有什么，不拥有什么

点击类别筛选。模块边界的核心不是目录，而是谁有权决定什么。

Core

src/core

定义全系统共同使用的领域语言和不可违反的规则，是最稳定、最不理解外部产品的一层。

  • 定义不可变输入：TaskCase、ExperimentSpec、CandidateSpec、RunPolicy。
  • 定义运行事实：RunAttempt、可选 RunManifest、RunRecord、RunOutcome、FidelityAssessment。
  • 维护七状态模型：检查每次状态转换是否合法，并规定 accepted、settled、finalizing 的推进门槛。
  • 定义公共端口：RuntimePort、EnvironmentPort、ControllerPort、ComparisonAgentPort 等接口及错误语义。
  • 验证不变量：failed 必须带 RunFailure，cleanup、fidelity、late event 和报告不能覆盖 outcome。
主要输入规范化领域命令、端口返回值、已持久化事件
主要输出公共类型、合法状态转换、领域验证结果
拥有：术语、公共 schema、状态机、RunOutcome 语义和跨模块不变量。
不拥有：具体产品协议、模型调用、文件存储、UI、用户协作策略；不导入具体 Product Pack、Pi 或报告实现。

Application

src/application

把各端口按确定顺序装配成三段业务流程；它负责“何时调用谁”，但不替专业模块做判断。

  • Case Preparation：导入完整历史会话，调用 Environment 解析 baseline，组装并原子冻结 TaskCase。
  • Candidate Run：为每个候选创建 run ID，解析 Runtime，准备隔离环境，启动 TargetRunner。
  • 推进协作循环：等待 settlement，组装 Controller 请求，先持久化 decision，再发送或结束。
  • 执行预算：统一处理墙钟、turn、模型调用、无进展、超时和用户取消等停止条件。
  • 统一收尾：所有路径进入 finalizing，停止 Runtime、采集 fingerprint、释放资源并固化 RunRecord。
  • 启动比较投影：运行结束后独立调用 Comparison 与 Renderer；失败不回写 CandidateRun。
主要输入TaskCase、ExperimentSpec、各端口实现
主要输出生命周期事件、RunAttempt、可选 RunManifest、RunRecord、比较投影请求
拥有：用例顺序、单个 CandidateRun 状态、预算执行、停止与收尾。
不拥有：恢复语义、用户下一句话、Target 工具执行、结果优劣解释和产品私有数据。

Product Packs

src/products

每个 Product Pack 是产品私有世界与 Harness 公共协议之间唯一的翻译边界，首个纵切片只静态注册 Codex；通过后再规划 Claude Code。

  • 发现与导入会话：定位产品 session，确定完整逻辑会话和第一条可执行用户输入。
  • 规范化历史事实：输出 transcript、historicalEvents、SourceRuntimeEvidence、环境线索和 artifact hints。
  • 发现当前 Runtime：记录 executable、版本、provider、实际模型和可观察关键配置。
  • 适配执行协议：将 start/send/stop 映射到原生接口，将私有事件归一化为 TargetEvent 与 TurnSettlement。
  • 确认边界事实：明确 delivery accepted/rejected/unknown，并给出原生或组合 settlement 证据。
  • 携带恢复知识：提供版本化 Recovery Playbook、fixtures、manifest 和 provenance hash。
主要输入私有 session、CLI/app-server 事件、当前安装与配置
主要输出ImportedSession、ResolvedRuntime、TargetEvent、TurnSettlement、Playbook
拥有：产品私有格式、Runtime 协议适配、Pack manifest 与恢复知识版本。
不拥有：SteeringContext、ComparisonContext、质量判断、环境隔离；不下载或切换 Runtime。

Environment

src/environment

把“历史任务开始前应有什么”转成经过证据验证、可为多个候选安全复制的环境基线。

  • 解析恢复目标：从 cwd、workspace、Git、文件历史、shell、浏览器与外部资源线索识别 required/optional 资源。
  • 管理 Recovery staging：只在 Harness 自有目录开放受限工具，向 Recovery Agent 提供只读证据。
  • 验证恢复声明：检查路径、hash、Git object、preimage 和来源证据，拒绝 Agent 自称成功但事实不成立。
  • 冻结 EnvironmentBaseline：逐资源记录 requested/recovered state、方法、置信度、证据、限制与 match 状态。
  • 准备候选环境：按 run ID 创建互不影响的可写副本或受控 observational 绑定。
  • 记录变化并释放：生成 before/after fingerprint、ChangeSet，并幂等释放 Harness-owned 资源。
主要输入EnvironmentSource、EnvironmentClue、EnvironmentPolicy、RecoveryResult
主要输出EnvironmentBaseline、PreparedEnvironmentRef、Fingerprint、ReleaseResult
拥有：恢复 staging、资源验证、baseline、候选副本、fingerprint 和环境资源 ownership。
不拥有：Runtime 启停、实验停止权、产品私有 schema；不写用户原目录，不保证外部世界可回滚。

Controller

src/agents/controller

在候选到达稳定输入边界后，模拟同等能力的人类协作者，为当前轨迹生成最合理的下一条输入。

  • 构造任务视图：读取完整原会话、initialInput、历史结果、用户偏好、约束、授权和能力证据。
  • 组装当前观察：把消息、工具、检查、claim、blocker、artifact、fingerprint 与 telemetry 汇成 TargetObservation。
  • 管理上下文：保留目标、安全边界、当前 turn 和已发消息；按预算压缩旧轨迹并保留证据引用。
  • 产生四类输入：continue、inform、correct、verify；只把自然语言 message 发送给 Target。
  • 判断何时结束：satisfied、blocked、requires_real_user_decision 或 no_further_value。
  • 验证与追踪：校验结构化输出、长度、控制字符、路径和 evidence ref，并单独记录 Controller 遥测。
主要输入SteeringContext、TargetObservation、PriorDecision、预算与权限边界
主要输出ControllerDecision：send(message) 或 done(reason)
拥有：同等人类能力下的协作判断、Observation Assembler、Controller session 与 decision trace。
不拥有：settlement 判断、Target 工具、环境写入、预算强制执行、结果评分或高影响授权。

Comparison

src/agents/comparison

在运行结束后，以原始完成结果为基线，为每个候选挑出最值得用户直接查看的结果与过程差异。

  • 组装只读上下文：把 TaskCase、BaselineEvidence、RunRecord、artifact、telemetry 与 fidelity 投影成公共视图。
  • 发现证据：列出、检查和受限读取 baseline/candidate artifacts，必要时做确定性文本或 JSON 比较。
  • 区分证据层级：把 Agent 自述、Runtime 事实、Harness 观察和确定性检查分开表达。
  • 选择高价值差异：优先任务产物和直接结果，随后才是过程效率、成本与模型自述。
  • 生成可追溯观察：每条 observation 携带 EvidenceRef，并明确证据不足和 fidelity 限制。
  • 支持降级：Agent 失败时退回客观遥测、原始消息与 artifact 清单，不影响运行完成。
主要输入ComparisonContext、只读 ComparisonTools
主要输出summary、observations[]、limitations[]
拥有：比较证据的选择、组织与简短说明，以及独立 Comparison session。
不拥有：统一评分、胜者排名、fidelity 判定、CandidateRun 状态、Runtime 控制和 artifact 修改。

Agent Host

src/infrastructure/pi-host

基于 Pi 提供三个 Agent 模块共同需要的模型基础设施，同时强制它们在会话和权限上彻底隔离。

  • 创建独立 session：Recovery、Controller、Comparison 分别配置模型、system prompt 与上下文。
  • 执行模型调用：通过 Pi provider API 调用用户配置的内部 Agent 模型。
  • 约束结构化输出：按各模块 schema 解析并报告非法响应，不把半截文本直接交给业务层。
  • 装配工具权限：Recovery 获得 staging 工具；Controller 与 Comparison 只获得各自允许的只读工具。
  • 采集调用遥测：记录模型身份、耗时、token、成本、工具调用与 provider 错误，并按模块归属。
  • 执行隐私过滤：发送模型上下文前应用 privacy policy 与敏感信息最小化。
主要输入模块 prompt、结构化上下文、工具白名单、Resolved Agent 配置
主要输出模型结构化响应、调用事件、模块级遥测
拥有：模型 session 生命周期、provider 调用、schema 输出和工具钩子基础设施。
不拥有：领域状态、RunOutcome、跨模块共享对话；不是万能 AgentModule 抽象或服务定位器。

Trace & Artifact

src/infrastructure/store

保存“真正发生过什么”，使状态、结果和报告都能重建、核验并追到原始证据。

  • 追加事件：在 Experiment 的唯一 events.jsonl 内分配 sequence、eventId、时间和 checksum，只追加不覆盖；run 视图按 runId 过滤。
  • 提交不可变 artifact：临时写入、关闭、计算 hash/长度、原子 rename，再追加 artifact.created。
  • 管理证据引用：校验 ArtifactRef / EvidenceRef 的 owner、来源事件、路径归属、存在性与 content hash。
  • 保存原始材料：长日志、stderr、截图、二进制和产品私有 raw 数据使用引用，不膨胀公共事件 schema。
  • 支持事件重放：从事件重建 state.json、RunRecord 和 comparison projection；末尾半行可截断，中间损坏必须报 corrupt。
  • 处理迟到事实：finished 后允许追加 late event，但禁止它改写已固化 RunOutcome。
主要输入领域事件、原生 Runtime 事件、Agent 调用、文件与环境证据
主要输出events.jsonl、artifact manifest、稳定 EvidenceRef、可重建投影
拥有：append-only 事实、artifact ownership、完整性校验和引用生命周期。
不拥有：事实的语义再解释、结果优劣、覆盖历史记录；缺失信息只能标 unavailable。

Report

src/report

把 ComparisonResult 和固定运行事实安全、确定性地投影为用户可以离线查看的本地 HTML。

  • 验证投影输入：检查 ComparisonResult schema、EvidenceRef 是否存在、归属是否正确。
  • 确定性布局：展示原始基线与候选结果、关键观察、限制、任务结果、停止原因和 fidelity。
  • 提供证据入口：只链接 experiment-owned 安全副本，长过程放入按需展开详情。
  • 安全渲染：统一 HTML 转义、内容长度控制和 media type 处理，避免模型内容注入页面结构。
  • 支持重复生成：相同 projection 与 artifacts 可重新生成报告，不依赖运行中的 Agent session。
  • 实现降级视图：Comparison 不可用时仍可展示客观消息、遥测、artifact 清单与诊断。
主要输入ComparisonResult、RunRecord、固定事实与安全 artifact 副本
主要输出自包含或 experiment-owned 的本地静态 HTML
拥有：转义、引用验证、页面布局和确定性呈现。
不拥有：语义选择、质量结论、fidelity 重算、运行状态；不暴露任意本机绝对路径。

CLI / TUI

src/cli

提供一个安装入口和最短用户路径，并把领域事件投影成可操作、可诊断的终端体验。

  • 首次设置：配置 Harness 内部 Agent provider/model、数据目录与隐私策略。
  • 发现和选择 Case：选择产品、浏览历史会话、查看导入诊断与环境恢复条件。
  • 创建实验：选择候选模型、确认当前 Runtime、共享 Controller 配置和 RunPolicy。
  • 展示运行时间线：区分 Target 活动、Controller 决策、实际发送输入、预算、warning 与 failure。
  • 处理用户动作：取消、打开诊断、查看 Runtime 详情、生成或打开本地报告。
  • 显式装配依赖：在 composition root 注册 Product Pack、Provider、Store、Agent Host 与 services。
主要输入用户选择、配置、领域事件、只读 projection
主要输出setup / cases / compare / report 命令与终端视图
拥有：用户导航、交互状态、终端渲染和应用依赖装配。
不拥有：业务事实和第二套状态机；关闭 TUI 不等于取消运行，UI 文案不改写领域结果。

05 · CandidateRun

一次候选运行如何推进

“消息已接收”“turn 已开始”“turn 已稳定”是三个不同事实；普通文本输出永远不自动等于 turn boundary。

created加载 Case
→
preparingresolve + prepare
→
launching启动并发送 initial
→
awaiting_target等待 settlement
⇄
awaiting_controller决策 send / done
→
finalizingstop / fp / release
→
finished只读 RunRecord
推进门槛
只有 delivery=accepted 才进入 awaiting_target；只有 settlement 才进入 awaiting_controller。
决策顺序
Controller decision 必须先持久化，再发送消息或进入收尾。
失败路径
任何失败都先进入 finalizing；不允许直接遗失进程或环境句柄。
终态不可改写
finished 后迟到事件可追加，但不能改变 RunOutcome；报告也不属于状态机。

Orchestrator

  1. prepare run
  2. resolve runtime
  3. persist manifest
  4. start / wait
  5. finalize

Environment

  1. fork baseline
  2. 返回隔离句柄
  3. after fingerprint
  4. release 自有资源

TargetRunner

  1. start(initial)
  2. delivery receipt
  3. stream events
  4. turn settlement
  5. stop

Controller

  1. 读取 SteeringContext
  2. 返回 send / done
  3. 不直接触碰 Runtime

Trace Store

  1. 状态转换
  2. 输入接纳证据
  3. Agent 决策
  4. artifact
  5. RunRecord
06 · Domain contracts

核心对象：谁是输入，谁是事实，谁是投影

避免最常见的误解：生命周期状态不是结果，历史 Runtime 不是执行约束，报告也不是事实源。

TaskCase

冻结的历史任务输入；完整逻辑会话默认就是一个任务。

source + initialInput + transcript
+ historicalEvents + BaselineEvidence
+ sourceRuntimeEvidence
+ environmentBaseline
+ privacy + provenance + contentHash

ExperimentSpec

用户想比较什么；实验级冻结 Controller、Comparison 配置与 Target RunPolicy。

taskCaseId + candidates[]
+ controller + comparison config
+ Target RunPolicy
+ outputRoot

RunAttempt / RunManifest

RunAttempt 先冻结最小身份；准备成功后才冻结完整启动条件。

RunAttempt: runId + experimentId + candidate request
RunManifest?: resolvedModel + ResolvedRuntime
+ PreparedEnvironmentRef + resolved Controller
+ Target RunPolicy

RunRecord

运行结束后的只读投影，可从事件重建。

RunOutcome + FidelityAssessment
+ final environment + traceRef
+ artifactRefs + warnings
维度回答的问题典型值绝不能混成
Lifecycle state运行走到哪一步？awaiting_target / finalizing / finished任务质量
TaskAssessmentController 看来任务是否完成？apparently_completed / incomplete / indeterminate进程是否退出
RunTermination为什么停止？completed / limit_reached / blocked / failed / uncertain环境匹配度
CleanupResultHarness 自有资源清干净了吗？complete / incomplete / unknown覆盖原终止原因
FidelityAssessment对照条件有多可信？strict / exploratory / observational运行成败
07 · Agent isolation

三个 Agent：共享 Host，不共享判断

Pi Agent Host 仅提供模型基础设施。每个模块使用独立 session、system prompt、上下文、工具权限与 trace。

准备阶段

Recovery Agent

处理证据不完整、来源异构、需要语义判断的环境恢复。只在 Harness staging 内使用产品 Playbook 与受限工具；最终是否恢复成功由 Provider 验证。

能：调查、选择恢复方法、在 staging 重建
不能：写用户原目录、宣称未验证事实成立
运行阶段

Controller Agent

面向候选当前轨迹，模拟与原用户能力、目标、约束相当的人。输出下一条普通用户消息，或 done reason。

send: continue | inform | correct | verify
done: satisfied | blocked
    | requires_real_user_decision
    | no_further_value
运行后

Comparison Agent

先看产物与确定性事实，再看 Agent 自述；输出少量有区分度且带 evidence ref 的观察。

summary + observations[] + limitations[]
不统一评分，不做候选排名，不改 outcome
硬隔离

Pi Agent Host

提供 provider、session、schema constrained output、只读工具钩子与遥测。它没有跨模块对话，也不拥有运行状态。

Recovery session ≠ Controller session
Controller session ≠ Comparison session
预算与 provenance：三个 Agent 的总调用、token、成本默认不设上限；单次 timeout、结构化修复和 provider 重试次数始终有限。Recovery 配置快照写入 TaskCase provenance，Controller 写入 RunManifest，Comparison 写入 comparison projection；RunPolicy 只约束 Target Runtime。
08 · Truth & recovery

事实来源：事件与不可变 artifact

第一版不用数据库，也不建设完整 Event Sourcing。目标是崩溃后不误判、不重复输入、不破坏当前工作区。

权威事实

  • Experiment 唯一 events.jsonl，单 writer lock，sequence + checksum
  • artifact 关闭后计算 hash，再原子 rename
  • case / experiment 以 complete 标记；attempt / manifest 以唯一事件提交
  • state.json、RunRecord、报告都是可重建投影
  • 中断恢复依据：已持久化事实 + 外部状态 + 幂等性

禁止猜测

  • stdout 静默不等于 turn settled
  • 写入 stdin 成功不等于 Runtime accepted
  • delivery unknown 时禁止自动重发
  • finalizing 崩溃不能猜为成功
  • 模型给出的 artifact 路径与 ID 不可信，必须校验 ownership 和 hash
输入提交链： controller.input_proposed → input.submission_started → input.submitted → runtime.input_accepted。只有最后一步才能推进候选 turn。
09 · Safety boundary

隔离、授权和诚实降级

“任务通用”不等于“所有环境都严格可恢复”。系统允许探索性运行，但不允许隐瞒条件差异。

边界强制策略无法满足时
文件系统路径规范化、root 包含检查、拒绝逃逸 symlink / junctionunsupported
候选工作区Harness 自有隔离副本；Runtime 只看到 PreparedEnvironment不直接运行
外部世界优先 mock / 测试账号 / 只读 API / 隔离 profileobservational
高影响操作发布、付款、删除、提权、不可逆迁移必须有历史明确授权或真实用户决定requires_real_user_decision
敏感信息privacy policy、密钥过滤、最小读取、trace 不记录凭据拒绝或 unavailable
模型与 Runtime同时保存请求别名与实际解析身份；未知就写 unknown降低 fidelity
10 · Implementation baseline

技术选型与刻意不做

首版追求最短可信纵切片，而不是提前为规模、插件市场或跨平台铺路。

已收口

  • TypeScript / ESM，Node.js ≥ 22.19.0
  • Windows 11 为首个正式支持平台
  • 首个纵切片仅静态注册 Codex Product Pack；通过后再规划 Claude Code
  • Pi agent-core / pi-ai / pi-tui 精确版本
  • TypeBox schema；单一 npm CLI；模块化单体
  • TUI 为事件投影；HTML 为简单自包含静态报告
  • 标准库优先，不预加 cross-spawn、diff 或模板依赖

当前不做

  • 历史 Runtime 下载、恢复或版本切换
  • 原始会话逐轮 replay
  • 通用 workflow DSL、消息队列、分布式执行
  • 插件市场、热加载、远程发现、DI 容器
  • 统一质量分与自动宣布胜者
  • 自动回滚不可逆外部副作用
  • 为尚未支持的浏览器、数据库、容器预建空 Provider
推荐实现顺序：先用 fixture、LocalWorkspaceProvider 与 ScriptedRuntime 走通 setup → compare → report，再完成 Codex 真实纵切片；只有形成可判断证据后才规划第二个产品适配。
11 · Implementation roadmap

按模块 0–8 分步交付

先完成确定性地基和 fixture 用户路径，模块 8 才运行真实 Codex；每个模块以前一模块的事实为输入。

模块 0 · 工程基线与开发约束

0

建立最小 TypeScript/ESM 单体骨架、版本约束和无副作用 CLI 入口。

  • Node.js ≥ 22.19.0、Windows 11 首发、严格类型检查。
  • 统一 src/core、application、products、environment、agents、infrastructure、report、cli。
  • 只安装已证明需要的依赖，不预建业务抽象。
退出条件：CLI help 可运行，版本与目录约定可复用。
不做：领域模型、Runtime、Agent、UI。

模块 1 · 领域契约与事实存储

1

固定 schema、七状态模型和唯一权威事件日志。

  • RunAttempt 先提交；准备成功后才提交可选 RunManifest。
  • Experiment 唯一 events.jsonl、单 writer lock、原子 artifact 与可重建投影。
  • 验证 EvidenceRef ownership、hash、状态转换和迟到事件。
退出条件：准备失败和启动后结束都能重建合法 RunRecord。
不做：产品协议、Agent、真实 Runtime。

模块 2 · Codex Product Pack

2

只实现首个静态注册的 Codex Pack 与历史会话导入。

  • 以 fixture 解析完整会话、initialInput、BaselineEvidence 与来源事实。
  • 发现当前 Runtime 和实际模型，未知项不推断。
  • 声明 start/send/stop 的核查能力及 uncertain 降级。
退出条件：可稳定生成不可变 TaskCase，私有 raw 数据不泄漏到 Core。
不做：Claude Code、动态 Pack 加载。

模块 3 · Environment 与隔离工作区

3

为首个空目录任务建立 Harness-owned 隔离环境和 Recovery 端口。

  • prepare、fingerprint、release 与失败均写入事实。
  • Recovery 只写 staging，Provider 负责验证和提交 baseline。
  • 不把候选 Runtime 指向用户原目录。
退出条件：可取得并幂等释放隔离目录，源目录不被触及。
不做：浏览器、数据库、复杂项目恢复。

模块 4 · 受控 CandidateRun

4

用 RuntimePort、TargetRunner 和确定性 Orchestrator 驱动七状态生命周期。

  • 严格区分 delivery、settlement、退出与 cleanup。
  • 只有 accepted 才等待 Target，只有 settlement 后才调用 Controller。
  • ScriptedRuntime 覆盖异常路径；unknown 不盲目重发。
退出条件：无 Agent 时所有合法与异常路径均可确定性验证。
不做：通用 PTY、第二 Runtime。

模块 5 · 受限 Agent Module

5

复用 Pi Host，但隔离 Recovery、Controller、Comparison 的 session、提示词、工具和 trace。

  • 统一 AgentConfig/ResolvedAgentConfig、schema 校验和确定性 fallback。
  • 只记录 Runtime/provider 实际提供的调用、token、成本；单次 timeout、修复和 provider 重试有限。
  • Recovery 只写 staging；Controller 只在 settlement 后决策；Comparison 只读证据。
退出条件：非法、越权或超时输出均安全降级，不改写事实。
不做：万能 Agent 抽象、跨 Agent 隐藏状态。

模块 6 · 比较投影与静态报告

6

把验证后的 ComparisonResult 和固定运行事实投影为安全、离线 HTML。

  • 证据引用校验、HTML 转义和安全 artifact 链接。
  • 相同 projection 生成相同语义报告。
  • Comparison 失败时降级为客观事实与诊断。
退出条件：恶意文本不能注入 HTML，无 Agent 结果仍可诊断。
不做：统一评分、候选排名、本地 server。

模块 7 · CLI/TUI 用户路径

7

以单一 npm CLI 串起 setup、cases、compare、report；TUI 只投影领域事件。

  • 先用 fixture + ScriptedRuntime 走通完整路径。
  • 关闭 TUI 转紧凑日志；第一次 Ctrl+C 取消，第二次强退并记录 interrupted。
  • composition root 静态装配 Codex Pack、Provider、Store、Pi Host 与 services。
退出条件：无需编辑内部文件即可完成确定性演示。
不做：daemon、detach/reattach、Web 控制面。

模块 8 · 真实 Codex 纵切片

8

只在模块 0–7 通过后，用受控真实任务验证产品假设与现有边界。

  • 任务使用空目录或冻结输入，无不可逆外部动作。
  • 记录输入、Runtime/模型身份、trace、artifact、fidelity、cleanup 与人工判断。
  • 只修复真实证据证明不足的共享边界。
退出条件：形成可判断证据，或可追溯地说明失败阶段。
不做：以模型胜负验收、公共 benchmark、提前适配 Claude Code。
阶段闸门：A（模块 0–1）固定地基；B（2–4）完成可控运行；先执行一次最小 Codex smoke；C（5–6）加入受限智能与证据；D（7）走通 fixture 用户路径；E（8）验证真实 Codex；F 仅在 E 形成可判断证据后规划 Claude Code。完整职责与验证见 docs/development-plan.md。
