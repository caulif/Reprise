# Reprise 成熟 TUI 完成后的产品规划

状态：后续规划
日期：2026-08-11
前置文档：[TUI 与最小用户交互规划](../product/tui.md)（原前置的交互式 TUI 实施规划已被取代并移出版本控制）

## 1. 前提

本文假设前置规划已经完成：用户可以在 TUI 中选择历史会话和候选模型，运行实验，并查看 Comparison 结果。

如果主流程尚不可用，先完成前置规划，不用后续功能掩盖缺口。

## 2. 第一性原理

Reprise 只需要帮助用户回答：

> 对这段真实历史任务，候选模型做得怎么样，我是否愿意使用它？

后续开发只服务于两件事：

1. 用户能轻松完成实验；
2. 用户有足够证据自行判断候选模型表现。

稳定、恢复、trace 和环境信息只是实现手段。除非它们阻碍体验或误导判断，否则不把它们当作开发目标。

## 3. 目标与边界

### Goal

用户无需理解 Reprise 内部结构，即可独立完成：

```text
找到历史会话
→ 选择候选模型
→ 看懂运行过程
→ 比较原始结果与候选结果
→ 作出自己的判断
```

### Acceptance Criteria

- 首次配置只询问必需信息，后续使用合理默认值；
- 每一步都对应真实用户决策，没有展示内部流程的多余页面；
- 运行中能看懂当前阶段、公开过程和可用操作；
- 结束后的 TUI 首屏足以形成初步判断；
- 本地并排报告可以核对回复、改动、命令和测试证据；
- Comparison 不替用户宣布唯一赢家；
- 一名未参与开发的用户无需说明或内部脚本即可完成流程。

### Non-goals

不开发统一总分、排行榜、云服务、批量调度、插件平台或推测性的产品扩展，也不展示或推断隐藏 chain-of-thought。

### Verification

让真实用户使用真实历史会话完成流程，观察其在哪里停住、看不懂或缺少判断依据。

### Risk Boundaries

Candidate 仍只操作隔离副本，不修改原仓库、Agent 全局配置或凭据。技术细节默认收起，但会影响用户判断的限制必须展示。

## 4. 接下来怎么做

只运行一个短循环：

```text
用户完成一次真实实验
→ 记录阻断、误解和缺失证据
→ 做最小修改
→ 再由用户使用
```

不要预先列功能清单。只有真实使用中出现的问题才进入开发。

问题只分三类：

- **阻断**：用户无法继续；
- **误导**：用户会错误理解候选表现；
- **摩擦**：可以完成，但步骤多、等待不清楚或证据难找。

按阻断、误导、摩擦的顺序处理。纯外观偏好不处理。

## 5. 修改时优先看什么

### 5.1 从启动到运行

自动发现可以自动发现的内容，提供合理默认值，收起高级选项。若一个页面不要求用户作决定，就删除或合并它。

### 5.2 运行过程

默认显示当前阶段、Candidate 的公开回复/计划/工具/命令、Controller 实际输入和取消操作。没有新事件时明确显示正在等待，不伪造活动。

### 5.3 判断结果

TUI 摘要按以下顺序展示：

1. 原始任务；
2. 原始结果与候选结果；
3. Candidate 的文件改动和验证结果；
4. Controller 是否追加输入；
5. 会影响比较的限制；
6. 完整并排报告入口。

报告沿用相同顺序，并允许用户展开到原始证据。不要让用户自己从长时间线中拼接结论，也不要用统一分数代替判断。

## 6. Done-means

一名新用户可以独立启动 Reprise、选择历史会话和候选模型、看懂运行状态、完成或取消实验，并依据 TUI 摘要与并排报告判断候选表现。开发者不需要解释 Harness、Runtime、Recovery 或 trace。

达到这一点后停止开发。没有新的真实用户问题，就不增加代码。

## 7. 之后是否扩展

只有用户明确需要测试 Claude Code 历史会话时，才实现最小 Claude Code Product Pack。先复用现有 contract，只有真实差异无法表达时才修改。

不因为“以后可能需要”而建设通用插件框架或同时支持多个 Agent 产品。
