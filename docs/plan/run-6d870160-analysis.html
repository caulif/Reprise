3. 为什么控制器会说“七轮什么都没做”

控制器每轮拿到的摘要几乎一字不差：

current Latest target settlement: completed. No model text is available to the Controller. Observed commands: 0; changed paths: 0; rejected approvals: 0. trajectory Settled turns: N; commands: 0; changed paths: 0; runtime-generated paths: 0. replay.isolation Writes stay in the isolated replica and never land in the original user directory.

这不是控制器“瞎编”，是 Host 喂给它的观察就是错的。三条机制叠在一起：

  1. 指纹只扫隔离副本。写到 C:\yanjiusheng\... 的文件永远不会出现在 changedPaths。
  2. 跨产品时 inspect 用了来源 Pack。experiment.ts 里 inspectRun(..., taskCase.source.productId)。来源是 Codex，候选事件却是 claude-code.*。Codex 翻译器认不出 Claude 的 Bash/Write，命令计数恒为 0。对照阶段的 inspect 用的是 candidate.productId，两边不一致。
  3. 隐私关了模型正文。No model text is available to the Controller。就算翻译器对了，控制器默认也看不到“文件已写到某某路径”那段回复。它被要求用 read_observation 自己翻 run_events，从七次 rationale 看，它没有据此纠正“零命令”这个摘要。

于是控制器按自己的规则第 3 条（普通用户回复解不开的无进展循环）给出 done/blocked。在它看见的世界里这个判定说得通；在真实文件系统里候选已经交卷了，只是交到了错误的目录。

5. 对照红字是另一件事

comparison.json：

{ "status": "failed", "failure": { "code": "agent_failure", "message": "Service temporarily unavailable, please retry later.", "attempts": 1, "kind": "transient_upstream" } }
  • 对照模型与控制器相同：providerId: dzzzz-openai，gpt-5.6-terra。
  • Reprise 把 503 / “service temporarily unavailable” 归类为 transient_upstream，只试 1 次（maxStructuredRepairAttempts: 1 管的是 JSON 修复，不是 HTTP 重试）。
  • 因此生成的是占位页 comparison-failure.html，不是对候选产物的评判。即使隔离没漏、控制器判对，这次对照也会因为上游不可用而失败。

8. 这不是什么

  • 不是 MiniMax 完全不会用工具（host-trace 里工具很密）。
  • 不是恢复没把 xlsx 放进隔离区（恢复报告写明根目录留了那份表；候选只是没去隔离根，去了提示里的旧路径）。
  • 不是对照模型判定候选差；对照根本没跑完。
  • 不是 maxConsecutiveNoProgress: 2 这条 Harness 硬停（那会是 stalled.no_progress）。停的是控制器策略。

9. 若要再跑，优先核对的点

  1. 看原目录那两份今天生成的 HTML，确认能否接受这次污染。
  2. 跨产品跑时，控制器观察必须用候选 Pack 翻译事件，而不是来源 Pack。
  3. 隔离若要成立：要么禁止 Runtime 写隔离根以外的路径，要么重放前改写/遮蔽历史绝对路径，不能只靠 cwd。
  4. 对照 503 与候选行为无关；上游恢复后再开对照，或给 transient 错误做有限重试。
