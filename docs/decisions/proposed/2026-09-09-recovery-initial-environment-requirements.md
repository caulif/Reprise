# 决策：Recovery 尽力恢复任务初始环境

状态：proposed

## 问题

现有 Recovery 更偏向恢复任务相关路径，无法充分表达用户期望的“恢复会话任务初始环境”。

## 决定

用户已确认本节需求；proposed 表示等待实现与验收生效，不要求重复确认设计。实施范围见[起点恢复目标](../../plan/recovery-initial-environment.md)。

Recovery 的目标时点是原始 Agent 接收 `initialInput` 之前；没有精确时间时，使用第一次可观察任务操作之前作为保守边界。目标是任务条件等价，并采取尽力恢复策略。

Recovery 可以在隔离副本中清理整个工作区，并可按判断删除、恢复、重建、安装依赖、构建或运行诊断。默认将无法证明在边界前存在、且在任务期间或之后出现的内容视为后继产物并清除。对于无法证明存在的环境内容，Agent 可根据任务需要保留或重建；不应盲目重建。

Recovery 主动从当前环境反推完整起点，而不是只应用已有 patch。若恢复缺口影响任务完成或改变任务难度则停止候选；若不影响则继续，并记录缺口。决策保持简单的保留/恢复或清除语义，不引入逐文件评分模型。

主流程只有一个连续 Recovery Session 和一个隔离工作副本，由 Recovery 自主调查、恢复和自检。Host 提供材料、工具和持久化，不预先铺开多套恢复路线。Recovery 判断任务条件是否恢复到位；Host 只拦截机械失败，并把可修复事实反馈给同一 Session。

Recovery 的最终结论简化为 `ready` 或 `blocked`：前者表示可以开始原任务，后者表示关键缺口影响任务。`unresolved` 只说明剩余问题，不表示评分或证据等级。输入收敛为任务、起点线索、可观察材料和能力边界，Agent 自主选择恢复路线，不由 Host 预设假设或候选。

上下文采用四项原则：有限预算优先保留当前任务最相关内容；历史和文件使用 Just-in-time retrieval，需要时再读取；压缩保留目标、不变量、已验证事实和未决问题；持久事实、临时思路、工具输出和进度分开保存。

Recovery 不新增 Todo、Plan 或 Goal 工具，也不引入完整业务状态机。Agent 在 Session 摘要中维护最小进度：当前目标、已完成动作、待检查项和阻塞原因。Host 仅保留运行生命周期、工具审计、取消、超时、边界检查和持久化状态；Recovery 的业务判断直接产生 `ready` 或 `blocked`。

Prompt 由稳定的 System Prompt 与三个固定 turn 组成。System Prompt 不规定任务资源、轮次动作或 JSON 格式；第一轮让 Agent 推导起点条件，第二轮自主恢复与准备，第三轮自检并按 Host 提供的输出契约结论。Session 上下文是主要承接方式；Agent 需要时可在副本的 `.reprise/recovery-work/` 留下短记录，必要内容自行迁移，临时目录不进入封存基线。

隐藏目录、Git 元数据、依赖、虚拟环境、缓存和工具配置均纳入按需判断。未知不等于已证明后继；清理前结合任务、当前内容与历史调查判断，不把缺少日志作为唯一删除依据。允许推断重建，但不能把推断内容宣称为历史原件。

Recovery 可以按需复用并修改本机开发环境，不引入容器或虚拟机作为前提。任务文件仍在隔离副本中恢复；本机依赖和工具配置的变化可能保留，不承诺随副本删除而撤销。环境准备与原任务由 Recovery 根据任务语义区分，不能替候选提前完成任务。

恢复成功后保存起点，每次候选运行复制独立副本，直接复用而不重新调查恢复。复用前轻量检查必要运行条件，发现缺失才调用 Recovery 修补运行副本或本机依赖，不修改保存的起点。

## 备选方案


**仅恢复已有证据**：实现简单，但无法满足从当前环境主动重建起点的目标。

**保留所有未知内容**：降低误删风险，但会把历史任务产物暴露给候选。

**逐资源评分**：信息更细，但增加复杂度，且不是本需求目标。

## 影响

现有 Recovery prompt、工具环境、候选清理策略、复用入口和验收规则需要在后续实施批次中调整；本记录只记录需求，不宣称实现已完成。任务源码和资料的恢复写入限于隔离副本，本机开发环境允许按需调整；凭据保护与禁止修改全局 Git 配置等既有边界保持有效。

## 验证

后续实现应能展示：历史任务产物被清除、起点文件被恢复、必要环境被按需重建，以及影响任务的缺口阻止候选启动。
