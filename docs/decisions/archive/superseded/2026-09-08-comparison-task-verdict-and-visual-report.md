# 决策：Comparison 按任务给出使用建议与可视化对照报告

状态：superseded

本提案由[真实任务比较卡](../accepted/2026-09-09-comparison-shareable-task-card.md)替代。正文保留为历史设计，不作为实施要求。

## 问题

用户希望运行结束后知道：这个模型在自己的真实任务上好不好用，是否值得用于下一次类似任务，以及相比历史方案究竟改变了什么。报告需要直接作出有依据的取舍，并用易读的 HTML 呈现两边差异。

[当前 Comparison 设计](../../architecture/comparison.md)以调查差异、供用户自行判断为目标。[提示词](../../../src/agents/comparison-agent.ts)明确禁止评分、排名和选赢家；[事实投影](../../../src/application/comparison.ts)提供运行与交付线索。这些能力能支撑调查，但没有要求评委回答“是否值得使用”。仅改页面样式不足以填补这个目标差距。

本提案承接已确认的方向：依据任务性质作出取舍，展示时间、token、速度等硬指标，最终仍由 Comparison 生成可视化 HTML。下文定义目标方案，不表示这些能力已经存在；本次只形成设计文档，不变更运行行为。

## 决定

### 1. 产品目标与判断范围

**Comparison 的主要产物是一份基于本次证据的使用建议，以及让人能自行核对该建议的双边可视化报告。**

报告回答三个问题：

1. 交付物是否达到这次任务的使用标准？
2. 得到它需要多少等待、沟通、检查和返工？
3. 相比历史方案，这次是否值得选择候选，下一次类似任务需要怎样监督？

分别给出“候选本次可用性”和“相对历史的选择建议”。候选可用不代表优于历史；历史结果也不是标准答案。两边都不达标时，可以明确建议都不选。

建议采用自然语言表达，例如“推荐用于类似内部草稿任务”“复核关键数据后可用”“本次不建议替换历史方案”“证据不足，暂不能建议替换”。不强制为所有报告套同一句式，不引入跨任务总榜或没有校准的综合分数。

单次报告的结论限于本次任务、配置和已观察行为。多次运行或多个任务的证据才能支持稳定性判断；不得把单次成功写成“长期可靠”。报告判断不修改 Controller 的任务判断、CandidateRun 状态或 RunOutcome。

### 2. 评价原则：先过门槛，再作取舍

先识别不可妥协的要求，再比较可交换的收益。核心要求失败，不能靠速度、低费用或漂亮排版抵消。

| 判断层 | 要回答的问题 | 例子 |
|---|---|---|
| 使用门槛 | 核心需求和明确约束是否满足？ | 计算正确、目标 bug 得到修复、文件可打开、指定内容齐全 |
| 质量收益 | 超过门槛的部分是否有实际价值？ | 解释更清晰、提案更有说服力、实现更易维护 |
| 用户负担 | 用户还要做什么，过程是否需要反复介入？ | 补充上下文、纠正已知要求、检查来源、修补遗漏 |
| 时间与费用 | 收益是否值得等待和支出？ | 一次可用比多轮返工更划算；快速草稿不值得过度打磨 |
| 信任与风险 | 是否存在隐蔽错误、越界操作或虚假完成陈述？ | 自称验证但无证据；未告知关键缺失 |

理解需求、工具使用、纠错和沟通作为上述判断的原因证据，不机械地按调用次数、问题数量或字数扣分。一次必要澄清可能避免返工，重复询问已给出的要求才可能增加负担。

| 任务性质 | 优先因素 | 取舍示例 |
|---|---|---|
| 紧急故障修复 | 修复有效、影响可控、及时恢复 | 可接受朴素实现，不接受无关重构引入风险 |
| 对外正式交付 | 准确性、完整性、呈现质量 | 有必要的检查和打磨值得额外等待 |
| 内部快速草稿 | 方向正确、尽快得到可修改结果 | 达标后优先节省时间，允许非关键细节粗糙 |
| 探索与讨论 | 有效思路、不确定性表达、交互节奏 | 多轮探索本身有价值，长延迟可能破坏体验 |

显式用户要求优先，其次是历史中有依据的偏好，最后是任务性质推断。推断必须在报告中简短说明；没有证据时不能臆造截止时间、预算或风险容忍度。若合理的不同偏好会反转建议，给默认建议并注明反转条件，不要求用户先填一套权重问卷。

### 3. 判断顺序

在同一个 Comparison Session 内完成以下工作，不因此引入多 Agent 或多个独立评判阶段。

1. **理解用途和输入范围。** 从任务、用户约束和历史要求识别用途。区分初始要求、后续澄清和新增范围；确认候选实际收到哪些信息。不能用它没有收到的新增需求证明其能力不足。
2. **先定标准。** 在阅读两边详细交付结果前，记录少量使用门槛和关键取舍因素，可复用现有工作笔记。要求核实后可以修订，但说明证据原因；不能为了支持偏好的结果事后移动标准。
3. **分别检查交付。** 两边按同一标准评估。文件、内容、可复核检查结果优先于最终回复；尚未检查不能标为满足。没有历史产物时保留缺失，不把历史自述当实物观察。
4. **检查关键过程。** 围绕会改变建议的纠偏、失败恢复、等待和遗留工作调查。先定位重要事件，再按需读取，避免完整复述日志。
5. **核对可比性和反证。** 区分结果差异、过程差异、配置差异和回放限制。对决定性结论检查最可能推翻它的证据。结果不佳与模型能力较弱不是同一个命题。
6. **作出任务相关建议。** 解释门槛是否满足，哪个收益值得哪个成本，剩余工作归谁，以及结论适用范围。局部证据不足不必阻止其他有证据的判断。
7. **编写 HTML。** 把建议、硬指标、决定性差异与证据组织为可视化报告。报告与一行摘要保持一致，不用强烈视觉暗示掩盖限定条件。

Controller 的交互只能支持“模拟用户提出了这些纠偏”的观察，不能直接换算真人分钟数、满意度或心理负担。历史有人类思考间隔，候选有自动 Controller 调度，两者轮数与墙钟时间必须标明差别。

### 4. 硬指标：顶部固定入口，数值与口径同时可见

顶部保留时间、token、速度和费用的紧凑对照区；两边采用相同顺序。数据缺失也保留指标名称并显示“未采集”，而不是隐藏较差或未知的一边。展开可查看来源、计算口径、覆盖范围和配置差异。

以下是目标展示语义，不是现有响应字段清单，也不承诺所有历史记录具备这些数据。

| 指标 | 展示口径 | 不能作出的推导 |
|---|---|---|
| 任务耗时 | 起始请求到终止的墙钟时间；可用时另列实际运行区间和用户等待区间 | 终止时间不能叫“到可用时间”，除非存在可用里程碑证据 |
| 首次响应延迟 | 同一测量层的请求发出到首个可见输出；多次调用注明统计范围和样本数 | 服务端 TTFT、客户端首字和首个有用结果不能混称 |
| 输出速度 | 有流式时间戳时，使用同范围输出 token / 对应生成时长，标明聚合方式 | 总 token / 总任务时长不能称模型生成速度 |
| Token 用量 | 输入、输出分开；缓存、推理用量按提供方含义展示，避免重复相加 | 不同 tokenizer 的 token 数不等于同样工作量；总量不直接等于成本 |
| 费用 | 有来源的实际费用；单位、覆盖角色和范围明确 | 不猜价格，不把缺失当免费，不把订阅费用摊成虚构单次价格 |
| 交互与工具 | 按需展开轮数、纠偏事件、调用成功与失败；注明模拟或真人 | 轮数少不直接代表省心，失败调用不直接代表任务失败 |

候选执行与 Recovery、Controller、Comparison 的开销分开。产品总等待可以单独展示，但不作为候选模型生成速度。只有同口径、覆盖完整的数据才计算差值与百分比；分母为零或条件不可比时展示绝对数及说明。缺失、部分采集、不适用、条件不可比是不同状态。

硬指标来源和算术由 Host 从已记录事实确定性产生，Agent 负责解释，不负责猜测计数。新增采集需求先检查现有事件与 Runtime 能力；不能仅在 prompt 中要求一个实际上没有采集的值。已有 token 摘要不等于已经具备完整双边流式测速数据。

### 5. HTML 阅读路径与视觉表达

保留 Comparison 作为 HTML 唯一作者、Host 原样发布的方式。固定用户必须得到的信息，不固定 DOM、组件库、配色或每份报告的章节数量。默认布局用于保证阅读顺序，具体表现由交付物和关键差异决定。

```text
┌──────────────────────────────────────────────────────────┐
│ 任务名称                     历史方案 A  /  候选方案 B     │
│ 耗时 A│B   token A│B   输出速度 A│B   费用 A│B   查看口径 │
├──────────────────────────────────────────────────────────┤
│ 明确建议：这次选谁 / 是否可用                              │
│ 决定性理由 · 为何适合这类任务 · 仍需用户做什么              │
│ 会影响建议的证据限制（如有，紧邻建议）                      │
├───────────────────────────┬──────────────────────────────┤
│ 历史交付                  │ 候选交付                     │
│ 同一要求下的内容/预览     ↔│ 同一要求下的内容/预览        │
│ 满足什么、缺什么          │ 满足什么、缺什么             │
├───────────────────────────┴──────────────────────────────┤
│ 关键要求对照 · 关键过程差异 · 为什么这样取舍               │
│ 展开证据 / 测量口径 / 配置与回放条件                       │
└──────────────────────────────────────────────────────────┘
```

首屏目标是在常见桌面视口同时看见主要硬指标和建议主体，不用大封面或装饰挤走结论。移动端将两边按同一比较项上下配对，保持标签；不要求窄屏强行容纳双栏。

交付对照优先展示最能改变选择的差异，而不是完整罗列所有文件：

| 交付类型 | 优先视觉形式 | 证据边界 |
|---|---|---|
| 页面、PPT、图像 | 对应区域并排预览、局部放大、差异注释 | 只有实际可取得的图像或渲染才能作为视觉观察；无预览时说明缺失 |
| 代码变更 | 用户行为前后对照、关键 diff、检查结果 | diff 大小不是质量；测试通过不替代需求核对 |
| 文本、调研 | 同一要求下的段落或主张对照、来源核查 | 篇幅长不是内容好；引用存在不等于支持该主张 |
| 数据与表格 | 同口径结果表、关键数字和公式检查 | 不用动画、面积或截断坐标夸大差异 |
| 无可读取产物 | 明确标注的回复摘录和已知检查证据 | 不绘制看似真实的交付物缩略图 |

不同指标使用各自单位的并排数值或条形图，必要时从零起轴；不把耗时、质量和 token 放进同一雷达图，不制造未经校准的能力刻度。颜色同时配文字或图标，不能仅靠红绿表达结论；历史与候选的位置和颜色全页一致。

交互只用于减少阅读负担：展开证据、查看配对预览、切换关键差异与全部差异。核心建议和数字在 JavaScript 禁用时仍可读；键盘可操作，文本有足够对比度，打印不丢结论。长日志默认折叠，证据入口紧邻对应判断。

报告自包含、默认离线，遵循现有相对证据链接、隐私和只读边界，不引入外部 CDN、远程字体、遥测或修改文件的交互。HTML 的自由创作不代表可以伪造截图、采集值或判断确定性。

### 6. 建议与证据的表达

每个决定性判断尽量同时交代：使用标准、两边观察、用户影响和证据入口。观察、推断与未知用简短文字明确区分，不输出没有校准的“置信度 93%”。

示例文案，仅用于说明表达方式，不对应真实运行：

> 这次更推荐候选用于内部草稿。两边都满足核心内容要求；历史版本排版更精细，候选更早给出可修改内容。对这类任务，额外排版收益不足以抵消等待。不过候选两处数据尚未验证，正式使用前仍需核对。当前证据支持这次取舍，不能证明重复运行同样稳定。

若缺少历史产物，可给出“候选本次可用”，同时说明“无法确定是否优于历史”。若运行被预算截断，说明当前配置未交付以及已观察进展，不推断增加预算必然成功或模型必然较弱。严重证据限制必须贴近结论，不藏在页尾。

### 7. 与现有架构衔接

复用 [单 Session attempt](../accepted/2026-09-08-comparison-single-session.md)、封存快照、briefing 索引、证据引用、失败不覆盖成功报告，以及 [Agent 编写 HTML](../accepted/2026-08-15-comparison-agent-authored-html.md) 的所有权。

实施时调整提示词目标：允许基于任务和证据推荐一方，要求先定标准并解释取舍；继续禁止虚假观察、能力误归因和篡改结果。该调整涉及 [自由报告形式](../accepted/2026-09-02-comparison-free-report-form.md) 的相关表述，生效时须精确说明替代范围，而非整体废弃 HTML 自由创作。

初始方案尽量沿用薄信封：一行摘要可承载使用建议，完整理由在 HTML 中。不为页面设计新建通用评分协议或渲染引擎。如果后续确有跨报告检索、聚合建议的需求，再定义结构化判断与迁移；机器消费者不能通过解析 HTML 猜建议。

硬指标补齐属于 Host 事实投影和采集工作。新增模型可见输入须可从事件复原；持久化和外部数据遵循现有 schema 校验。保留旧记录读取能力，缺失采集不阻止生成有边界的报告。

本提案不改变对照的显式启动策略。用户启用对照后得到此报告；是否默认每次运行都调用 Comparison，以及相应费用和等待，是单独的产品选择。

### 8. 实施顺序

1. 选取少量有代表性的真实历史案例，人工写出可用门槛、关键证据、可接受的建议范围。覆盖结果失败、过程费劲、质量与速度取舍、历史证据缺失。
2. 盘点双边硬指标来源，先使用真实可得数据；定义单位、时间范围、角色范围与缺失语义，再决定必要的采集改动。
3. 调整 Comparison 调查与写作目标，在现有单 Session 中生成任务相关建议和 HTML；不同时扩展到多候选排名。
4. 用案例检查判断质量和可视化表达，验证关键结论在顺序交换、冗长干扰等条件下是否保持合理。
5. 生效时同步当前架构、产品和相关 ADR，按实际改动运行工程门禁。真实模型评价沿用显式 opt-in；文档方案本身不触发计费调用。

## 备选方案

**固定权重总分。** 易排序，但不同任务的门槛和偏好差异大，分数会掩盖不可接受的核心失败。选择任务门槛与自然语言取舍，保留真实硬指标。

**继续只列差异。** 能保持中立，但把判断负担全部交还给用户，不满足本次产品目标。选择让 Agent 给建议，并开放证据供用户核对。

**只改 HTML 模板。** 能统一视觉，不能保证标准、证据和取舍正确。选择信息要求与自由视觉表达结合，不增加 Host DOM 内容门禁。

**默认多评委投票。** 可能减少某些随机偏差，但增加费用且无法消除共同偏差。先以真实案例校准单评委，只有误判证据支持时再讨论额外评审。

## 影响

Comparison 将从差异调查者承担到任务相关的建议责任，但不成为运行状态裁决者。用户不必自行从 trace 推导结论，同时仍能查看原始依据。

时间、token 与速度的可靠呈现取决于双边采集质量，旧历史不一定能补齐。报告必须容纳不对称证据；不得为了双栏美观生成虚构对称数据。

评委可能偏爱冗长、熟悉的风格或模型品牌。适用时先以中性 A/B 查看交付，再结合配置解释成本和限制；最终报告仍显示真实身份。盲化不能删掉影响公平性的环境条件。

研究和社区反馈作为设计依据，不能作为具体模型的性能结论：论文结果局限于各自实验；社区讨论是非代表性样本，部分评论涉及旧模型或不同工具组合。本轮研究核对了下列论文摘要与讨论内容，没有复现论文实验。

| 来源 | 对本方案的启发 |
|---|---|
| [MT-Bench / Chatbot Arena](https://arxiv.org/abs/2306.05685) | 模型评委可近似人类偏好，但要处理位置、冗长和自我偏好 |
| [Length-Controlled AlpacaEval](https://arxiv.org/abs/2404.04475) | 字数是评价混杂因素，不能把冗长当质量 |
| [Prometheus](https://arxiv.org/abs/2310.08491) | 细化标准与参考材料有助于任务相关评价 |
| [Agent-as-a-Judge](https://arxiv.org/abs/2410.10934) | 调查产物和过程比只读最终回复更符合 Agent 任务 |
| [τ-bench](https://arxiv.org/abs/2406.12045) | 关注实际状态、用户交互与重复运行可靠性 |
| [Sonnet 4.5 讨论](https://news.ycombinator.com/item?id=45415962)、[DeepSeek R1 讨论](https://news.ycombinator.com/item?id=42768072) | 用户关心决策质量、等待、价格、工具可靠性和日常交互 |
| [实际编码案例](https://simonwillison.net/2025/Jan/27/llamacpp-pr/) | 质量可以值得额外等待，但人的测试和提示工作应被看见 |

## 验证

以下是实施验收目标，不是本次文档验证的通过声明。

| 场景 | 可观察的期望 |
|---|---|
| 核心结果错误，速度快且表达漂亮 | 建议不因速度或排版跨过使用门槛 |
| 两边都达标，一边更精细但更慢 | 依据任务用途解释是否值得等待，不能只列优缺点 |
| 必要澄清与重复纠偏 | 区分交互价值，不按轮数机械扣分 |
| 历史产物缺失 | 不把自述标成验证；可评价候选，不强选相对赢家 |
| 预算截断、环境或工具不匹配 | 描述实际体验及原因边界，不直接归因模型能力 |
| 后续新增要求未提供给候选 | 标注输入不对称，不当作同条件失分 |
| 硬指标缺失、部分采集或零值 | 不补零、不猜价格、不生成失真的百分比或速度 |
| Controller 代替真人 | 明确模拟交互，不声称测得真人节省时间 |
| A/B 交换顺序、隐藏品牌、增加无关篇幅 | 决定性判断不应无证据反转；记录反转案例并校准 |
| HTML 首屏和证据导航 | 读者无需原始日志即可找到硬指标、建议、差异和剩余工作；关键判断可到达证据 |
| 窄屏、键盘、禁用 JS、离线 | 核心信息仍可读，配对关系和来源标签不丢失 |
| 单次成功 | 不生成长期稳定性、普遍能力或无条件替换建议 |

确定性验证检查数值口径、缺失处理、证据归属与发布边界；真实案例评价检查建议是否有依据、是否符合任务取舍；浏览器检查布局与交互。三者不能相互替代，也不以固定措辞或组件快照证明判断正确。

人工校准先记录可接受建议与理由，再看评委结果，避免以评委答案倒推标准。重点记录会误导选择的错误及其证据，不要求所有主观偏好完全一致。最终让读者能回答：这次选谁、为什么、还要做什么、结论在哪里可能不成立。
