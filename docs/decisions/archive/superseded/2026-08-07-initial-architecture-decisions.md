## ADR-001: 采用动态 Controller 而非逐字重放

### 状态
已接受

### 背景
原始会话中的用户消息是针对原模型的轨迹。被测模型走到不同状态后，直接重放原始消息会产生问题：
- 被测模型可能缺少必要的澄清
- 被测模型可能收到不自然的提示

### 决策
使用独立的 Controller（基于 Pi Agent）根据当前被测模型的轨迹动态生成下一条用户输入。

### 理由
1. **理论支撑**：Mixed-initiative interaction、Grounding、Scaffolding 理论表明人类协作是动态的
2. **现实对应**：真实用户会根据 Agent 当前表现调整输入
3. **公平性**：「同等能力边界」比「相同文字」更合理

### 后果
- ✓ 更接近真实人机协作
- ✓ 被测模型获得适合其轨迹的帮助
- ✗ Controller 本身成为实验变量
- ✗ 需要固定 Controller 版本保证可比性

### 替代方案
1. **逐字重放**：简单但不自然，已否决
2. **混合策略**：部分重放 + 部分动态，过于复杂，暂不考虑

## ADR-002: 只测量模型在实际 Agent 产品中的效用

### 状态
已接受

### 背景
可以选择测量：
- 基础模型的纯能力（通过统一 API）
- 模型在实际 Agent 产品中的表现（Claude Code、Codex）

### 决策
固定 Agent 产品（runtime、tools、system prompt），只替换底层模型。

### 理由
1. **用户视角**：用户购买和使用的是 Agent 产品，不是裸模型
2. **真实性**：包含了 runtime 的提示词、工具策略、压缩逻辑
3. **实用性**：回答「我是否应该在 Claude Code 中换模型」

### 后果
- ✓ 结论对用户决策有直接价值
- ✓ 无需重新实现 runtime 的复杂逻辑
- ✗ 结果包含 runtime 的影响，不是纯模型能力
- ✗ 闭源 runtime 的内部细节可能无法验证

### 替代方案
1. **统一 API 测试基础模型**：失去 runtime 的真实影响，已否决
2. **同时测量两者**：工程量翻倍，暂不考虑

## ADR-003: 复用 Pi Agent Core 而非重新实现

### 状态
已接受

### 背景
Controller 需要一个 Agent 框架来：
- 管理模型调用
- 处理上下文
- 记录事件

### 决策
使用 `@earendil-works/pi-agent-core` 实现 Controller。

### 理由
1. **避免重复造轮子**：Pi 已经提供成熟的 Agent Core
2. **聚焦核心价值**：Harness 的价值在实验编排，不在 Agent 框架
3. **保持简洁**：不需要维护自己的模型接口、事件系统
4. **品味一致**：Pi 的设计哲学（少量原语、事件流、组合）符合本项目

### 后果
- ✓ 快速启动，专注于实验逻辑
- ✓ 复用 Pi 的模型切换、事件、遥测能力
- ✗ 依赖外部项目，需要跟进 Pi 的变化
- ✗ 如果 Pi 不满足需求，切换成本较高

### 替代方案
1. **自己实现 Agent 框架**：工程量大，偏离核心价值，已否决
2. **使用 LangChain/LangGraph**：过于重量级，已否决
3. **直接调用 Anthropic SDK**：需要自己处理上下文、事件、重试，已否决

## ADR-004: 不建立统一质量评分

### 状态
已接受

### 背景
可以选择：
- 为所有任务输出统一分数（如「模型 A 8.4 分」）
- 展示任务相关的证据，让用户自己判断

### 决策
不计算统一质量分，只展示客观遥测（时间、token、成本）和任务证据（diff、测试、截图）。

### 理由
1. **任务异质性**：编码任务看测试通过率，研究任务看信息完整性，无法统一
2. **主观性**：「代码质量」「用户满意度」难以客观量化
3. **误导风险**：单一分数掩盖了差异的复杂性
4. **用户能力**：用户最了解自己的任务，能做出更好的判断

### 后果
- ✓ 报告诚实、可追溯
- ✓ 避免误导性的精确分数
- ✗ 用户需要自己解读证据
- ✗ 无法跨任务汇总「哪个模型总体更好」

### 替代方案
1. **LLM-as-a-judge 评分**：引入第三个模型，增加不确定性，已否决
2. **用户打分**：主观性高，难以跨用户比较，暂不考虑
3. **混合指标**：加权平均多个维度，过于复杂，已否决

## ADR-005: 诚实标记实验强度而非假装完美复现

### 状态
已接受

### 背景
有些任务环境无法完全复现（外部网站变化、数据库状态、未提交的文件）。

### 决策
采用四级标记：
- `strict_match`：runtime 和环境均可验证匹配
- `version_mismatch`：runtime 版本或配置不同
- `environment_mismatch`：环境状态不同
- `observational`：只能观察一次运行，无法对照

### 理由
1. **诚实性**：承认现实限制，不隐藏不确定性
2. **可信度**：让用户知道结论的强度
3. **实用性**：即使是 `observational`，也有探索价值

### 后果
- ✓ 结论强度透明
- ✓ 避免虚假的完美复现承诺
- ✗ 用户需要理解四级标记的含义
- ✗ 部分任务只能做到 `observational`

### 替代方案
1. **只支持可完美复现的任务**：限制太大，失去价值，已否决
2. **假装所有任务都可复现**：不诚实，误导用户，已否决
3. **二级标记（可复现/不可复现）**：粒度太粗，已否决

## ADR-006: 第一版只支持 Claude Code

### 状态
已接受

### 背景
可以选择：
- 第一版支持多个产品（Claude Code、Codex、Cursor）
- 第一版只支持一个产品，做好再扩展

### 决策
第一版只支持 Claude Code，当有 10+ 用户需求时再支持其他产品。

### 理由
1. **聚焦核心**：验证「动态 Controller + 对照实验」的价值
2. **避免维护负担**：每个产品的适配器都需要维护
3. **工程效率**：做好一个比做 10 个浅尝辄止更有价值
4. **接口提取时机**：有第二个实现时再提取 RuntimePort 接口

### 后果
- ✓ 快速验证核心假设
- ✓ 代码简洁，维护负担小
- ✗ 只能服务 Claude Code 用户
- ✗ 后续扩展时可能需要重构

### 替代方案
1. **第一版支持多个产品**：工程量大，延迟验证，已否决
2. **先支持 Codex**：Claude Code 有更好的事件流支持，已否决

## ADR-007: Controller 第一版只做 nextUserMessage

### 状态
已接受

### 背景
设计文档提出 Controller 有三个能力：
- `proposeRecovery`：推理环境恢复计划
- `nextUserMessage`：生成下一条用户输入
- `selectEvidence`：选择报告要展示的证据

### 决策
第一版 Controller 只实现 `nextUserMessage`，其他两个用简单规则。

### 理由
1. **核心价值**：`nextUserMessage` 是动态协作的核心
2. **简单规则足够**：环境恢复用「有 git commit 就用，没有就 copy」
3. **证据选择可固定**：「diff + 测试输出 + 最后消息」覆盖大部分情况
4. **避免过度设计**：三个能力的上下文不同，放一起会混淆

### 后果
- ✓ Controller 职责单一，易于调试
- ✓ 快速验证核心价值
- ✗ 环境恢复可能不够智能
- ✗ 证据选择不能适应所有任务

### 扩展时机
- 环境恢复失败率 > 30% 时，引入 `proposeRecovery`
- 用户频繁抱怨「报告没展示我关心的内容」时，引入 `selectEvidence`

## ADR-008: Append-only 事件流而非可变状态

### 状态
已接受

### 背景
可以选择：
- 用可变对象存储运行状态，结束时序列化
- 用 append-only 事件流，每个状态变化都记录

### 决策
采用 append-only 事件流，每个事实追加到 `events.jsonl`。

### 理由
1. **可追溯性**：完整记录发生了什么，不丢失中间状态
2. **可调试性**：出问题时可以回放事件序列
3. **可恢复性**：进程中断后可以从事件重建状态
4. **理论支撑**：Event Sourcing 的成熟实践

### 后果
- ✓ 完整的审计日志
- ✓ 支持中断恢复（未来）
- ✓ 可以从事件生成不同视图的报告
- ✗ 事件文件可能较大
- ✗ 需要设计事件 schema

### 替代方案
1. **内存状态 + 最终序列化**：丢失中间状态，调试困难，已否决
2. **数据库存储**：过于重量级，已否决

## ADR-009: 保存原始产品事件到 raw/

### 状态
已接受

### 背景
不同产品的事件格式不同。可以选择：
- 只保存归一化后的事件
- 同时保存原始产品事件和归一化事件

### 决策
原始产品事件完整保存在 `raw/` 目录，归一化事件保存在 `events.jsonl`。

### 理由
1. **信息完整性**：归一化可能丢失产品特有信息
2. **调试需要**：出问题时需要看原始输出
3. **未来扩展**：后续可能需要用到原始事件中的字段
4. **版本兼容**：产品升级改变事件格式时，原始事件仍可用

### 后果
- ✓ 信息无损
- ✓ 调试友好
- ✗ 存储空间增加
- ✗ 需要维护两套事件

### 替代方案
1. **只保存归一化事件**：信息丢失，已否决
2. **在归一化事件中嵌入原始事件**：events.jsonl 变得难以阅读，已否决

## ADR-010: 第一版环境恢复用简单规则

### 状态
已接受

### 背景
环境恢复可以：
- 用 Agent 推理恢复计划（复杂但智能）
- 用简单规则（简单但可能不够智能）

### 决策
第一版用简单规则：
```text
if (hasUncommittedChanges) {
  copyToTempDir();
} else {
  useCurrentDir();
  recordGitCommit();
}
```

### 理由
1. **验证需求**：不确定复杂恢复是否真的需要
2. **工程效率**：简单规则覆盖大部分编码任务
3. **风险控制**：Agent 推理可能出错，简单规则更可靠
4. **渐进式**：先用简单规则，发现问题再优化

### 后果
- ✓ 快速实现
- ✓ 可靠性高
- ✗ 无法恢复历史 commit（用户需手动 checkout）
- ✗ 无法处理复杂环境（浏览器、数据库）

### 扩展时机
- 环境恢复成为主要痛点时，引入 Agent 推理
- 需要支持浏览器/数据库环境时，引入专门的 Provider

## ADR-011: Turn boundary 优先用原生事件

### 状态
已接受

### 背景
判断 Agent 完成一轮可以：
- 解析文本输出（不可靠）
- 使用产品原生事件（可靠但可能没有）
- 用 quiet period 启发式（兜底）

### 决策
优先使用产品原生事件（如 Claude Code 的 `turn.completed`），没有时再考虑 fallback。

### 理由
1. **可靠性**：原生事件是产品的权威边界
2. **简单性**：不需要猜测和解析
3. **渐进式**：第一个产品有原生事件，后续产品再考虑 fallback

### 后果
- ✓ Turn 边界准确
- ✓ 代码简单
- ✗ 依赖产品提供事件
- ✗ 不支持没有事件的产品（暂时）

### 未来扩展
- 支持第二个产品时，如果没有原生事件，再实现 composite / heuristic 策略
- 第一版不做复杂的 turn boundary 识别

## ADR-012: 报告第一版用 Markdown

### 状态
已接受

### 背景
报告可以：
- Markdown（简单但不美观）
- HTML（美观但需要模板和样式）
- Web 应用（交互但工程量大）

### 决策
第一版用 Markdown，后续改进为 HTML。

### 理由
1. **快速验证**：Markdown 生成简单，专注于内容
2. **可读性**：Markdown 可以直接在编辑器、GitHub 查看
3. **渐进式**：先验证报告内容是否有用，再优化展示

### 后果
- ✓ 快速实现
- ✓ 版本控制友好（纯文本）
- ✗ 不够美观
- ✗ 无法做交互式对比

### 升级计划
- M4 改进报告时，用简单模板引擎生成 HTML
- 不追求复杂的前端应用

## ADR-013: 预算默认值保守但允许调整

### 状态
已接受

### 背景
需要设置预算防止无限运行。可以：
- 固定预算，不允许调整
- 默认预算，用户可覆盖

### 决策
默认预算为：
- 30 分钟墙钟时间
- 12 个 target turns
- 单 turn 5 分钟超时
- 60 秒 heartbeat

用户可通过配置文件或命令行参数调整。

### 理由
1. **安全兜底**：避免失控运行
2. **用户体验**：默认值对大部分任务够用
3. **灵活性**：允许调整应对特殊任务

### 后果
- ✓ 运行不会失控
- ✓ 大部分用户无需关心预算
- ✗ 少数复杂任务需要手动调整

## ADR-014: 不追求实时进度反馈

### 状态
已接受

### 背景
运行可能持续 5-30 分钟。可以：
- 实时显示进度（WebSocket、流式更新）
- 运行结束后展示结果

### 决策
第一版运行结束后展示结果，不做实时进度。

### 理由
1. **工程复杂度**：实时进度需要 WebSocket 或轮询
2. **价值有限**：大部分用户可以等待 5-30 分钟
3. **渐进式**：先验证核心价值，再优化体验

### 后果
- ✓ 代码简单
- ✓ 快速验证核心价值
- ✗ 用户不知道运行进度
- ✗ 中途出错需要等到结束才知道

### 未来优化
- 如果用户频繁抱怨「不知道进度」，再添加简单的日志输出或进度文件

## 决策原则总结

所有决策遵循以下原则：

1. **理论驱动**：有明确理论依据才引入复杂度
2. **渐进式**：从简单规则开始，根据实际需求升级
3. **可逆性**：优先选择容易回退的方案
4. **删除优先**：没有第二个真实实现时不创建抽象
5. **诚实性**：承认限制，不假装完美

## 如何使用本文档

- 当考虑新功能时，先检查是否有相关决策
- 当质疑现有设计时，回顾决策理由和权衡
- 当决策需要推翻时，新建 ADR 记录变更和原因
- 保持 ADR 简洁，只记录关键决策

## 更新规则

- 新增决策：添加新的 ADR-XXX 章节
- 推翻决策：标记原 ADR 为「已废弃」，新建 ADR 说明原因
- 不修改已有决策内容（保持历史可追溯）
