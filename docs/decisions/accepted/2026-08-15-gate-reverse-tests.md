# 决策：新增或修改门禁必须附反向用例

状态：accepted

## 问题

门禁可以在「干净树上退出 0」的同时什么都不验。生成区正则匹配失败时 `--check` 恒绿；帧分析器没接线时溢出被固化成基线；文档自检写了却从不运行。只看绿灯会把失效检查当成质量证据。

## 决定

新增或修改门禁时，同一次变更必须附一个能让该门禁失败的自动化用例。只验证「干净树上退出 0」不构成门禁生效的证据。覆盖率阈值只升不降；降低必须更新[覆盖率决策](./2026-08-14-coverage-thresholds.md)并写明为什么覆盖面变小可接受。

## 备选方案

**只在文档里写「手工改坏再跑一次」。** 这正是本轮三个假绿门禁的来源：反向步骤不会在每次改门禁时自动跑。

**用 allowFailure 先挂上再补反向用例。** 观察模式没有退出条件就会永久停在装饰状态。

## 影响

- `verify:docs`、`gen-docs --check` 和帧比对在正式检查前先跑自检。
- 改门禁脚本时必须能指出哪一条自动化用例会在检查失效时变红。
- 覆盖率数字贴实测值向下取整，下调走决策记录而不是先改 `package.json`。

## 验证

- `npm run verify:docs` 输出包含自检结论。
- 生成区插入垃圾文本后 `npm run verify:generated` 退出非 0。
- 人为对齐的错误帧会让 `tui-visual-audit.mjs --check` 退出非 0。
