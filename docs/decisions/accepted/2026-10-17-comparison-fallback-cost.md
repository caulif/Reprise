# 决策：Comparison 缺失用量的独立补估

状态：accepted

## 问题

上游暂态失败后成功重试可以完成报告，但 SDK 的失败全零 usage 是占位值，不能作为免费事实。一次缺失便让整次 Comparison 没有总估价，不利于操作者理解成本。需要保留可核对的已知部分，并提供明确标注的回退估价。

## 决定

- Pi 每次实际生成或压缩请求创建独立 `requestId`，贯穿 `agent.model_request`、`agent.usage_reported` 和流诊断；同一输入的重试使用不同 ID。旧日志缺字段时继续走原来的归属规则，不补造历史用量。
- SDK 返回 error/aborted 全零占位 usage 时，文本请求可产生独立 `agent.usage_estimated`，不写成 `agent.usage_reported`。失败已有非零 usage、成功明确为零的用量仍按原规则记录。补估事件经核心 schema 校验后持久化，带请求 ID、模型、scope、算法版本、脱敏失败分类和消息及估算 token。
- `pi-character-heuristic-v1` 复用 SDK 的消息字符估算（约四字符一个 token），加入系统提示、工具定义及每条消息八 token 的固定开销；输出仅计已返回的文本、thinking 和工具调用。输入全部按普通输入计费，不假定缓存命中。它不是匹配模型的精确 tokenizer，不还原隐藏生成，不是实际账单或严格上界。原生图片请求不按 base64 长度估算，继续保留缺口。
- Comparison 按实际模型和既有 override/catalog 给两种事件定价，保存价格来源、版本和费率。资源账本和离线评测共用按请求 ID 归集的费用账本；`knownEstimatedCostUsd` 只包含上报 usage 的静态估价，`fallbackEstimatedCostUsd` 独立汇总补估。全部请求均有可定价记录时，`estimatedCostUsd` 可以包含补估，必须伴随 `costBasis=includes_fallback` 和补估请求数。仍有缺记录或缺价格时总额保持未知，已知部分继续可见。
- 同一请求后到的真实 usage 替换补估，不重复计费；补估不能覆盖真实 usage。评测的 `usage`、`usageCoverage` 仍只描述真实上报，补估不提高用量覆盖率。旧报告、冻结 facts 和旧 journal 不原地改写。
- `pricingIncomplete` 保留保守语义：有补估或未知都为 true。金额硬保护不因存在回退数字而认证成本完整，缺失 usage 时仍拒绝继续；无金额上限时，既有时间、请求和工具保护不变。补估价格会进入已知预算消耗比较，但不是供应商消费上限保证。
- 目前不接入渠道账单查询，不引入新 tokenizer 依赖，不把 Comparison 开销混入历史/当前 Runtime 指标。补估方法和来源先保存在私有账本、评测及工具反馈中，不增加报告两侧的任务费用。

## 备选方案

**始终不给总额。** 最保守但掩盖已知部分，不满足操作者需要的参考总额。

**把失败算零或复制成功重试费用。** 无法证明未计费，也不能假定两次请求缓存及输出相同，故不采用。

## 影响

新增事件和可选字段是增量协议；旧日志没有补估时不因升级被重新估算。旧 reader 可忽略新事件与附加字段，但不能将其认证为完整的上报费用。未来任何回填必须保留独立来源及原始记录。

## 验证

逆例覆盖失败全零、不丢非零失败 usage、成功零用量、独立重试 ID、补估审计失败、图片缺口、价格未知、迟到上报替换、无归属记录、重复 ID、金额保护，以及从持久化事件离线重算。模拟 Provider 验证协议，不宣称验证供应商实账；本轮不调用真实模型。
