# 决策：覆盖率阈值只升不降

状态：accepted

## 问题

`test:coverage` 已经能产出总体百分比，但不设阈值、也不进 CI。覆盖率因此只能当本地观察，下降不会挡住合并。不写下来的数字半年后没人知道为什么是这三个整数，下一次改阈值时会重新争论「要不要留缓冲」。

## 决定

用 Node 自带的 `--test-coverage-lines` / `--test-coverage-branches` / `--test-coverage-functions` 卡住总体覆盖率，不引入 vitest 或 c8。阈值取 2026-08-14 在拆完 `controller.ts` / `experiment.ts` 之后的实测值，各向下取整、不留缓冲：

| 指标 | 实测 | 阈值 |
|---|---|---|
| lines | 88.08% | 88 |
| branches | 76.49% | 76 |
| functions | 87.41% | 87 |

排除清单只写测试、脚本、纯类型产物和 CLI 入口（`dist/test/**`、`dist/scripts/**`、`dist/src/**/types.js`、`dist/src/cli/main.js`）。`src/tui/` 不排除：渲染正确性由 TUI 帧基线承担，行覆盖率只保证业务逻辑不悄悄消失。

阈值只升不降。提高必须有新的实测值；降低必须先更新本记录并写明为什么覆盖面变小是可接受的。未覆盖的行优先当死代码删除，而不是补一个只为过门禁的测试。

## 备选方案

**不设阈值，只在本地看报告。** 这是改之前的状态。没有失败信号，覆盖率下降要靠人记得去看，而人不会每次都看。

**按文件 100%，再用豁免清单消化未覆盖行。** 这是 dsh 的做法，需要 exempt-heavy 双 lane、自定义 reporter 和一份持续维护的豁免表。单包、TUI 占源码约三分之一的仓库里，这三套设施的维护成本高于它挡住的回归。

**阈值留 2–3 个点的缓冲。** 缓冲等于允许覆盖率先降再补。本门禁的目的就是不让覆盖面无声缩小，留缓冲会把它变成装饰。

**把 `src/tui/` 整目录排除，把阈值抬高。** 这会让 TUI 里抽出的业务逻辑（例如 `page-input.ts`）再掉出覆盖率视野。帧基线管渲染，不管按键分发和状态应用是否还被测到。

## 影响

- `package.json` 的 `test:coverage` 带上三个整数阈值；`npm run check` 仍然不跑覆盖率，避免本地全量门禁再付一遍测试时间。
- CI 的 `coverage` lane 跑 `npm run test:coverage`，下降即红。
- 拆文件或删死代码之后，应以新的实测值提高本记录中的阈值，而不是继续沿用 2026-08-14 的整数。

## 验证

- 2026-08-14 在当前树上跑 `npm run test:coverage`，总体行为 88.08 / 76.49 / 87.41。
- 写入 88 / 76 / 87 后同一命令退出 0。
- 人为去掉一个被测函数的调用后，同一命令因阈值失败。
