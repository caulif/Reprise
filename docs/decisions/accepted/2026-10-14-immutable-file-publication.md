# 决策：不可变文件使用无覆盖原子发布

状态：accepted

## 问题

Store 的不可变 JSON 写入先 stat 再调用可替换的 writeAtomic。并发调用都可能通过存在检查，后来的 rename 覆盖已发布事实。writeImmutable 原来只是 writeAtomic 的别名，调用者无法从原语取得真正无覆盖的保证。

## 决定

- writeAtomic 继续原子替换可变投影；writeImmutable 单独实现不可变字节创建，writeImmutableJson 仅负责序列化并使用该原语。
- 在目标同目录独占创建私有临时文件，写完并关闭句柄，再通过文件系统 hard link 创建目标。链接创建只有一方能成功，读者只能看到不存在或完整内容，目标存在即拒绝。
- 目标文件系统不支持 hard link 时明确失败，不回退 rename、复制或对最终路径直接 wx 写入。不将文件协议用于冻结目录发布。
- 只删除本次拥有的临时文件；发布前的失败不动目标，发布后的清理失败也不回滚目标。清理失败用 AggregateError 保留原错误（如有）、发布状态及临时路径，调用者不得将未知创建结果当成安全覆盖重试。
- 底层不比较内容。持久化调用者仍承担 schema 和身份校验；已有 Store artifact 的完整配对、owner、hash 与提交事件校验及同内容幂等契约保持不变。私有冻结 staging 内文件可以使用相同原语，但其目录可见性仍由既有发布协议负责。
- 不改变 JSON 格式，不迁移历史事实，不新增 fsync 或断电持久性保证。

## 备选方案

**直接对目标 wx 写入。** 可避免覆盖，但会暴露部分写入，因此不采用。

**先 stat 再 rename，或仅依赖 writer lease。** 前者存在竞争窗口；后者不能保护原语的独立调用以及 lease 取得之前的事实写入。采用 hard link 使无覆盖性由文件系统原子操作保证，并保留完整可见性。

## 影响

不可变写入现在会拒绝原来错误允许的覆盖；JSON 和事件格式保持兼容。目录冻结仍使用原协议，尚未修复的生命周期问题不由文件原语代替解决。

## 验证

Windows 11 本机实际文件系统回归覆盖同进程八方和两个独立子进程的竞争、既有文件/目录/junction 不变、完整字节可见性、取消、写入失败、不支持链接及发布后清理失败。故障回归通过标准 fs 模块对象注入，不增加生产测试开关。其他文件系统仍需要验证 hard link 支持；不支持即失败，不作跨平台能力承诺。
