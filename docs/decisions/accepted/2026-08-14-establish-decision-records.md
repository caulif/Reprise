# 决策：建立决策记录

状态：accepted

## 问题

改动理由此前没有归宿。`git log` 只有 3 个 commit，而工作树一度有 236 个未提交变更，因此「为什么这么做、放弃了什么」既不在 commit message 里，也不在任何受控文档里——它只存在于聊天记录。

在没有归宿的情况下，理由自己找了两个替代出口，两个都更差：

- **累积式审查文档**：`optimization-round-4/5/6` 连续三轮，条目大量交叉，没有生命周期，也没有「本轮结论已被下一轮取代」的机制。读者无法判断哪一条仍然有效。
- **计划文档里的免责声明**：`second-product-packs-decision-brief.md` 开头写着「本文第 1.2 节曾建议 dsh 使用官方 SDK client，该建议未被采纳」。一份文档不得不在开头声明自己部分失效，说明缺的正是取代机制。

后果是同一个问题会被重新讨论。`docs/documentation-structure.md` 原先明确写「当前不建立正式 `decisions/` 目录…避免把阶段性讨论升级为制度」——这个判断当时是对的，但它担心的事情已经以更差的形式发生了：阶段性讨论确实升级成了制度，只是以无格式、无生命周期的审查文档形式。

## 决定

`docs/decisions/{proposed|accepted|superseded}/YYYY-MM-DD-topic.md` 承载长期约束实现的选择。生命周期由目录表达，状态变化就是移动文件；日期是首次提出的日期，移动时不改。

正文固定五节：`## 问题` / `## 决定` / `## 备选方案` / `## 影响` / `## 验证`。`## 备选方案` 强制存在，且只记录真实考虑过的方案——没有记录到被否方案的决策会被反复重新讨论。格式与触发条件的完整定义见[文档结构与路径约定](../../documentation-structure.md#决策记录)，由 `npm run verify:docs` 检查。

改动跨模块协议、on-disk 或 wire 格式、Agent 提示词契约、工具面、工程流程或门禁时，同一次变更必须新增或更新一份记录；纯机械改动豁免。

同时停止新增累积式审查文档。已执行完毕的审查移入 `docs/.local/`，仍未闭合的条目留在 `plan/`。

## 备选方案

**维持现状，理由写进 commit message。** commit message 是正确的变更叙述载体，但它按变更组织而非按主题组织：一个决策被三次变更逐步落地时，理由散在三条 message 里，且无法表达「这个决策取代了那个决策」。它是决策记录的补充，不是替代。

**沿用 dsh 的 Agent Notes 全套机制**（6 类分类目录、双语三件套、冻结归档 + blob hash 密封）。这些设施解决的是 542 份笔记规模下的问题：分类是为了在数百份笔记里检索，密封是为了防止归档被误编辑。我们几十份的规模下，分类只会制造「这算架构还是流程」的无效讨论，密封没有要防的问题。只取路径编码生命周期 + 强制备选方案两条。

**继续用 `analysis/` 承载决策。** `analysis/` 的定义是「某一时点的审查结论，非规范性」，与「长期约束实现」直接矛盾。让同一个目录同时承担两种权威等级，正是当前混乱的来源。因此 `analysis/` 目录整体取消。

**只写 `accepted/`，不要 `proposed/` 和 `superseded/`。** 少一层目录更简单，但会丢掉两个真实需求：拍板前的提案需要一个不被误当成规范的位置；被取代的决策需要保留可追溯性而不污染当前视图。

## 影响

- 每次非机械改动多写约 200 字，换来的是同一问题不再被重新讨论。
- `docs/documentation-structure.md` 中「当前不建立正式 `decisions/` 目录」的段落被本记录取代，该文件已相应改写。
- `docs/analysis/` 目录取消：仍有未闭合工作的 4 份移入 `plan/`，其余 5 份移入 `docs/.local/`。
- `decisions/superseded/` 收纳既有的两份历史决策：早期架构决策记录（原 `archive/2026-08-07/design-decisions.md`）和极简报告设计（原 `archive/2026-08-13/designs/report-design.md`）。它们冻结，不检查格式。
- 新增一个会失败的门禁：格式不符或状态与目录不一致时 `npm run verify:docs` 失败。

## 验证

- `docs/decisions/` 存在，且本记录本身满足它定义的格式——这是自举证据。
- `npm run verify:docs` 检查 `proposed/` 与 `accepted/` 的首行标题、状态行与目录一致性、五节齐全、`accepted/` 中不出现「将会」「计划」这类未来时标题。
- `docs/documentation-structure.md` 中不再出现「不建立正式 `decisions/` 目录」。
