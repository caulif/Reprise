# Reprise 项目路线图

## 项目定位

一个**本地优先**的、**克制的**、**理论驱动**的个人 Agent 对照实验工具。

**核心问题**：在我的真实任务上，换个模型会不会更好？
**核心价值**：把「感觉」变成「可追溯的对比报告」

## 设计原则

```text
理论清晰 > 功能丰富
代码简单 > 架构完美
事实优先 > 智能推理
删除优先 > 扩展优先
```

## 里程碑

### M0: 核心假设验证 (1 周)

**目标**：用最简代码验证「动态 Controller 是否可行」

**交付物**：
- 一个 200 行的 TypeScript 脚本
- 能读取历史会话、启动 Claude Code、用 Pi 生成下一条输入
- 跑通 1-2 个真实会话

**验证点**：
- Pi Controller 生成的输入是否合理？
- 能否完成简单任务？
- Turn 边界判断是否准确？

**如果失败**：说明核心设计有问题，需要调整理论假设

---

### M1: 单会话对照 (2-3 周)

**目标**：能对比一个会话在不同模型下的表现

**功能范围**：
```text
✓ 手动指定历史会话路径
✓ 手动指定目标模型
✓ 启动 Claude Code + Pi Controller
✓ 记录事件到 events.jsonl
✓ 生成 Markdown 报告

✗ 自动发现会话
✗ 环境恢复（直接在当前目录运行）
✗ HTML 报告
```

**代码结构**：
```text
src/
├── experiment.ts       # 状态机：准备 → 运行 → 等待 → 完成
├── claude-code.ts      # 启动 CLI，解析 stream-json
├── pi-controller.ts    # 基于 Pi 的 nextUserMessage
├── trace.ts            # append-only 事件存储
├── report.ts           # 生成 Markdown 报告
└── cli.ts              # 命令行入口
```

**报告内容**：
1. 运行条件（模型、时间、环境）
2. 客观指标（时间、token、成本、turn 数）
3. 关键差异（第几轮开始不同）
4. 最终产物（diff、最后消息）

**验证点**：
- 用 3-5 个真实会话测试
- 人工评估 Controller 质量
- 报告是否帮助决策

---

### M2: 环境隔离 (1-2 周)

**目标**：避免污染用户当前目录

**功能范围**：
```text
✓ 检查 git status
✓ 有 uncommitted changes → copy 到临时目录
✓ 运行后清理临时目录

✗ 恢复历史 commit（用户可手动 checkout）
✗ 复杂的 fingerprint
✗ 浏览器/数据库环境
```

**实现**：
```typescript
interface Environment {
  prepare(): Promise<{ workDir: string; gitCommit?: string }>;
  cleanup(): Promise<void>;
}
```

**验证点**：
- 运行后当前目录无污染
- 临时目录正确清理

---

### M3: 会话发现 (1-2 周)

**目标**：自动列出本机历史会话

**功能范围**：
```text
✓ 扫描 ~/.claude/sessions/
✓ 提取任务摘要（从第一条消息）
✓ 按时间排序
✓ 用户选择运行

✗ 会话质量评分
✗ 智能推荐
✗ 批量运行
```

**CLI**：
```bash
reprise list                    # 列出历史会话
reprise run <session-id>        # 运行对照实验
```

---

### M4: 改进报告 (1 周)

**目标**：让报告更易读

**功能范围**：
```text
✓ 并排对比（原始 vs 新运行）
✓ 高亮差异（第几轮分叉）
✓ 展示关键证据（diff、测试输出）
✓ 客观指标图表

✗ 复杂可视化
✗ 交互式报告
✗ 自定义证据选择
```

**报告格式**：HTML（用简单模板引擎）

---

## 后续扩展（按需）

以下功能**不在前 4 个里程碑**，只有在有明确需求时才做：

### 扩展 1: 更多 Runtime
- 支持 Codex、Cursor 等其他产品
- 提取 RuntimePort 接口
- **触发条件**：有 10+ 用户要求支持其他产品

### 扩展 2: 智能恢复
- 用 Agent 推理恢复计划
- 支持恢复历史 commit
- **触发条件**：环境恢复失败率 > 30%

### 扩展 3: 证据选择
- 用 Agent 选择要展示的证据
- 支持用户偏好（更关心性能/测试/可读性）
- **触发条件**：用户频繁抱怨「报告没展示我关心的内容」

### 扩展 4: 批量运行
- 一次运行多个会话
- 生成汇总报告
- **触发条件**：用户需要「模型全面评估」

### 扩展 5: 更多环境
- 浏览器 profile 副本
- 数据库 mock
- 文档/表格快照
- **触发条件**：有具体的非编码任务需求

## 时间线

```text
Week 1:  M0 核心假设验证
Week 2-4: M1 单会话对照
Week 5-6: M2 环境隔离
Week 7-8: M3 会话发现
Week 9:   M4 改进报告

Total: 9 周首个可用版本
```

之后根据实际使用反馈决定是否做扩展功能。

## 不做清单

明确**不会做**的功能，避免范围蔓延：

- ✗ 公共 benchmark 排行榜
- ✗ 统一质量评分系统
- ✗ 复杂的插件市场
- ✗ 远程运行 / 云端服务
- ✗ 实时协作 / 多人共享
- ✗ 通用 Agent 平台
- ✗ 完美的环境复现（VM/Docker）
- ✗ 自动化 A/B 测试
- ✗ 机器学习优化 Controller

## 成功标准

**3 个月后**，项目应该能：

1. 用户能用 10 分钟完成一次对照实验
2. 报告能帮助用户做出「是否换模型」的决策
3. 代码库 < 2000 行（不含依赖）
4. 核心文件数 < 15
5. 有 20+ 真实使用案例

**不追求**：
- Star 数、下载量
- 支持所有产品
- 完美的复现率
- 漂亮的 UI

## 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| Controller 质量差 | 中 | 高 | M0 提前验证，必要时调整 prompt |
| Claude Code 事件格式变化 | 中 | 中 | 保存 raw events，适配层解耦 |
| 环境恢复失败率高 | 高 | 中 | 诚实标记，不强求完美 |
| 用户不知道如何解读报告 | 中 | 高 | 增加说明文档，简化报告 |
| 功能范围蔓延 | 高 | 高 | 严格遵守「不做清单」 |

## 关键决策记录

### D1: 为什么只用 Pi 实现 Controller？
- Pi 已经提供 Agent Core、事件、模型切换
- 不需要重新实现 Agent 框架
- 可以专注于实验编排逻辑

### D2: 为什么第一版不做环境恢复？
- 大部分会话可以在当前目录安全运行
- 复杂的恢复增加失败率
- 先验证核心价值，再优化细节

### D3: 为什么不统一评分？
- 不同任务的「好」标准不同
- 统一分数容易误导
- 展示事实比计算分数更有价值

### D4: 为什么不支持多个 Runtime？
- 每个产品的适配器都要维护
- 核心价值不在于「支持所有产品」
- 做好一个比做 10 个浅尝辄止更有价值
