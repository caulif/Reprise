# Controller 设计深度分析：理论、实证与设计依据

状态：理论稿 v2.0
日期：2026-08-07

> 本文回答“为什么这样设计”。工程接口、生命周期和实现步骤见[同等人类协作与 Controller 设计](../architecture/controller.md)。

## 1. 问题定义

Reprise 要比较的是：同一个用户在真实任务中，把 Claude Code 或 Codex 所使用的模型替换后，任务结果、过程效率和成本是否改变。

被测对象不是裸模型，而是：

```text
模型 + 当前已安装 Agent runtime + 工具/权限 + 任务环境 + 用户协作
```

难点在于用户协作不是固定脚本。候选模型的执行路径不同，历史会话中的下一条用户消息可能不再自然。无条件 replay 会让候选模型被迫接受另一条轨迹产生的提示，或者在缺少必要反馈时被不公平地卡住。

因此需要一个 Controller：它根据原始会话体现出的用户能力和当前候选轨迹，动态生成下一步用户输入。

## 2. 核心命题：同等能力，不是相同文本

### 2.1 固定什么

同一 Experiment 的候选运行应尽量固定：

- 原始任务和用户目标；
- 用户已经体现出的背景知识、偏好、权限和验收意图；
- 当前 Agent runtime、工具、MCP、权限、沙箱、provider 解析、压缩和重试设置；Harness 自动记录这些可观察事实，不恢复历史版本；
- Controller 模型、版本、system prompt、观察策略和安全预算；
- 可比较的起始环境。

### 2.2 不固定什么

以下内容应允许随候选状态变化：

- 后续用户消息的具体文字；
- 用户输入的时机和次数；
- Agent 的工具调用和执行路径；
- 产物、验证方式和停止时间。

更强模型少获得几次帮助，是实际产品效用的一部分，不是公平性缺陷。公平的对象是用户能力边界和任务条件，而不是完整轨迹。

### 2.3 Controller 的准确定位

Controller 不是：

- 理想专家；
- 原始用户的语言风格模仿器；
- 另一个执行任务的 Agent；
- 质量评分器；
- 完整的用户画像或策略状态机。

Controller 是：

> 一个受原始会话证据约束的监督控制器，代表这个用户在当前任务中的目标、知识、偏好、权限和验收能力，并在候选 Agent 到达输入边界时决定发送什么或是否停止。

## 3. 理论基础

### 3.1 Mixed-initiative interaction

人和系统可以动态决定谁在何时取得主动权。对 Harness 的直接推论是：Controller 首先要判断是否需要用户介入，而不是每一轮都生成消息。Agent 正常运行时不调用 Controller；到达稳定输入边界后才决定继续、干预或停止。

### 3.2 Grounding 与共同认知

协作需要持续建立共同理解。原始会话只记录过去的共同认知，候选 Agent 走到不同状态后，原消息未必仍然适用。Controller 必须根据当前状态重新判断缺失事实、目标偏差和验收证据。

### 3.3 Scaffolding

帮助应与执行者当前困难相匹配，并在其能够自主完成时撤除。由此得到两个约束：过度干预会掩盖模型自主能力；干预过少会把用户正常反馈错误地变成模型失败。

### 3.4 Joint cognitive system 与 distributed cognition

结果属于“用户 + Agent runtime + 模型 + 工具 + 工作环境”的联合系统。diff、截图、测试输出、文件和页面都是共享认知的一部分。Controller 只看 Agent 自述，会把会汇报误当成做得好；Controller 拥有隐藏环境，则会获得真实用户没有的能力。

### 3.5 Supervisory control 与 management by exception

监督控制通常是：系统自主运行，监督者观察，在偏差、风险或需要决策时介入。Controller 因此应当默认放手，只在信息缺失、方向偏离、证据不足或必须停止时行动。

## 4. 现实协作证据及其边界

公开研究对本项目有三类启发：

1. Claude Code 大样本分析显示，人更常承担目标、约束和规划，Agent 更常承担局部执行；这支持“人和 Agent 在不同抽象层分工”。
2. Web Agent 协作研究显示，用户有放手、选择性协作、持续监督和接管等不同模式；这些适合作为运行后的描述标签，不应成为运行前必须识别的 persona。
3. 人机协作综述和 AI pair programming 研究表明，领域知识、验证习惯和信任校准会改变协作结果；不能只测模型输出文本。

这些研究不能直接推出所有任务都采用相同的干预比例。编码研究不能代表浏览器、文档、桌面应用或业务系统；研究中的百分比也不应直接变成运行时阈值。

## 5. 从理论到设计的推论

### 5.1 用户能力的四个维度

| 维度 | 说明 | Controller 来源 |
| --- | --- | --- |
| 目标能力 | 知道任务为何重要、什么结果有用 | 原始目标和最终验收 |
| 领域能力 | 事实、术语、偏好和约束 | 历史用户消息和明确背景 |
| 监督能力 | 发现偏差、风险和过早完成 | 用户历史纠正、验证和拒绝 |
| 授权能力 | 哪些操作可自动做、哪些需确认 | 权限、风险和历史确认 |

这四个维度是提示和分析框架，不是运行时评分。

### 5.2 四类发送意图

- `continue`：上一轮已到输入边界，用户交还执行权；
- `inform`：补充用户已经掌握的事实、偏好或约束；
- `correct`：纠正目标、计划或产物的可识别偏差；
- `verify`：要求 Agent 建立会影响验收的证据。

`wait` 属于 Runner 生命周期，不是 Controller 消息。`clarify` 不作为第一版普通消息：低风险、可逆的未知选择可委托 Agent；高风险、不可逆且原始会话无偏好时，应诚实停止并标记 `requires_real_user_decision`。

### 5.3 观察边界

Controller 应观察真实用户正常可以看到的只读状态，而不是只看 Agent 已经读取的内容：

| 类型 | 示例 | 处理 |
| --- | --- | --- |
| 轨迹事实 | 消息、工具事件、工具结果、原生状态 | 提供 |
| 用户可见产物 | diff、当前文件、截图、页面、已有测试输出 | 通过声明式 adapter 提供 |
| 隐藏状态 | 密钥、未展示文件、后台数据库、任意 shell | 禁止 |

被动投影和格式转换可以由 Harness 完成；运行测试、网络请求、业务操作和修改状态属于主动探测，不由 Controller 执行。

### 5.4 历史信息与答案泄漏

完整原始会话可以用于理解用户能力、目标和偏好，不需要复杂的逐轮裁切系统。但 Controller 不应把原 Agent 后来调查得到的任务答案伪装成用户原本知道的事实。这个边界由固定 system prompt、trace 和人工抽查维护，而不是增加第二个审查 Agent。

### 5.5 System Prompt 如何表达“同等能力”

Prompt 不能只要求“模拟原始用户”，因为这容易退化成语言风格模仿或历史消息 replay。一个理论上合格的 Controller Prompt 至少应固定四类条件：

1. **能力同一性**：所有候选共享用户的目标、知识、偏好、权限和验收能力；
2. **状态适应性**：具体消息由当前候选状态决定，文本和干预次数允许不同；
3. **观察对称性**：所有候选使用同一类用户可观察证据，而不是同一份静态观察；
4. **职责分离**：Controller 负责协作输入，Target Agent 负责执行，Harness 负责权限、生命周期和报告。

优秀 Agent Prompt 的共同特征不是篇幅长，而是把角色、目标、边界、完成条件、失败处理和输出协议分开说明。Codex/Claude Code 的公开运行方式也将任务输入、工具权限、审批、原生事件和最终输出分层处理。本项目应学习这种结构，而不是猜测或复制闭源内部 system prompt。

Prompt 只能把同等能力变成稳定实验条件，不能证明 Controller 与真实用户完全等价。Controller 的误判、随机性和对隐性知识的遗漏必须通过 trace 暴露，而不是用更复杂的 Prompt 假装消除。

## 6. 理论上诚实的停止条件

Controller 不应为了让运行继续而伪造用户决定。以下情况应停止：

- 结果已满足目标且证据足够：`satisfied`；
- Agent/runtime 已无法继续：`blocked`；
- 需要真实用户作高风险或不可逆决定：`requires_real_user_decision`；
- 继续运行不再增加有效信息：`no_further_value`。

原生 `turn_completed` 只表示一轮稳定结束，不自动表示任务完成。

## 7. 研究和解释限制

- Controller 自身可能有随机性和判断偏差；
- 原始会话可能没有记录用户隐含知识；
- 环境、外部网站和权限变化会削弱因果解释；
- 一两个真实任务可以帮助个人决策，但不能推出模型的普遍排名；
- 产物质量存在主观判断，因此报告展示证据，不输出跨任务总分。

报告应同时展示：当前 Runtime 事实与实验内漂移 warning、Environment 匹配状态、Controller 消息和 intent、证据引用、时间、token、成本、工具调用、失败、重试和停止原因。

## 8. 结论

同等人类协作的核心不是复刻历史文本，而是固定用户能力边界，让同一个监督者在不同候选状态下自然行动。最小且有理论支撑的循环是：

```text
Target Agent 运行
    -> 到达稳定输入边界
    -> Controller 观察用户可见状态
    -> send(continue/inform/correct/verify) 或 stop(reason)
    -> Target Agent 继续或结束
```

理论只负责解释为什么需要这个循环；不应被翻译成复杂 persona、评分器或多代理状态机。

# 详细理论补充

本部分保留原研究稿中的详细推理，用于后续讨论。它不改变前文的 Canonical 结论，而是解释这些结论是怎样一步步得到的。

## A. 真实人-Agent 协作的观察框架

### A.1 规划和执行是不同的控制层

真实协作不能简单问“谁做得更多”。更有用的拆分是：

| 控制层 | 典型问题 | 更常由谁承担 |
| --- | --- | --- |
| 目标层 | 做什么、为什么做、什么结果有价值 | 人 |
| 约束层 | 哪些事实、偏好、权限不能违反 | 人和 Agent 共同维护 |
| 计划层 | 采用哪条路线、拆成哪些步骤 | Agent 提议，人监督 |
| 执行层 | 搜索、编辑、调用工具、运行命令 | Agent |
| 验收层 | 是否真的完成、是否可以接受 | 人，Agent 提供证据 |

Claude Code 大样本研究中“用户更多承担规划、Agent 更多承担执行”的发现，应理解为这种层级分工，而不是两个百分比的总和必须等于某个固定数值。对 Harness 的启示是：Controller 主要模拟目标、约束和验收，不应替 Agent 重新规划每一个局部动作。

### A.2 协作模式不是固定人格

真实用户会出现几种可观察模式：

- **Hands-off**：任务低风险或用户高度信任，主要在最后查看结果；
- **Collaborative**：在关键节点补充信息，然后把主动权交回 Agent；
- **Hands-on**：频繁查看和纠正，尤其在方向不稳定或结果难以观察时；
- **Takeover**：出现严重偏差后用户接管，后续不再让 Agent 自主推进。

这些模式受任务熟悉度、风险、环境可逆性、Agent 当前表现和用户时间影响。它们是运行轨迹的解释标签，不应预先把用户归入某一类。

### A.3 真实输入不只有纠错

从真实 Codex 会话可以观察到，用户输入经常是：

- “继续”“接着做”“开始”；
- “可以”“按这个方案”“照你的推荐”；
- 补充路径、错误日志、目标、偏好和验收标准；
- “这个不对”“重新思考”“结合项目实际”；
- “更新文档”“直接修改”“运行测试”；
- 收窄范围、拒绝不需要的功能或改变优先级。

因此只设计“发现错误后纠正”会低估 Controller 的工作。`continue` 是交还主动权，`inform` 是补充共同认知，`correct` 是改变方向，`verify` 是要求证据。

## B. 理论之间的关系

### B.1 Mixed-initiative 决定“谁在什么时候说话”

Mixed-initiative 理论解决的是主动权问题。它并不告诉 Controller 消息内容，而是提供一个调度原则：Agent 自主进行时不打断，只有当新的人类信息具有足够价值时才介入。

### B.2 Grounding 决定“为什么同一句话不能 replay”

Grounding 理论说明，协作双方的共同认知会随着每一步改变。原始用户说“继续”时，双方可能已经知道某个计划、文件和风险；候选模型没有走过同样路径时，这句话不一定有相同意义。

### B.3 Scaffolding 决定“帮助应当多大”

帮助不是越多越好。Controller 若把完整解决方案直接告诉弱模型，测量的是 Controller 的执行能力；Controller 若始终沉默，测量的是 Agent 在没有真实用户反馈时的能力。正确目标是提供用户在当前状态下合理会提供的最小有效帮助。

### B.4 Joint cognitive system 决定“测量单位是什么”

模型性能不只存在于模型输出中。一个更准确的系统边界是：

```text
用户目标和知识
    + Controller 的动态协作
    + Agent runtime 的提示、工具和权限
    + 模型的规划与执行
    + 工作环境和外部反馈
    = 任务级效用
```

所以固定 Claude Code/Codex runtime 不是在声称测量裸模型；它是在测量用户真实使用的产品条件。

### B.5 Supervisory control 决定“何时只观察、何时干预、何时停止”

监督控制可以看成一个反馈循环：

```text
期望任务状态 -> 观察当前状态 -> 估计偏差和证据充分性
             -> 放手 / 补充 / 纠正 / 验证 / 停止
             -> Agent 改变状态
```

Controller 不需要维护一个复杂的人工策略状态机，但必须拥有足够的当前状态观察，否则无法执行监督职责。

## C. “同等人类能力”的精确定义

### C.1 能力条件而不是消息分布

设任务为 `T`，用户能力边界为 `U`，runtime 和环境为 `R,E`，候选模型为 `M`。一次运行可抽象为：

```text
trajectory = Run(T, U, R, E, M, Controller)
```

比较时希望固定 `T,U,R,E,Controller`，改变 `M`。由于 Controller 读取当前轨迹，后续消息可以不同，但消息生成规则属于同一个 `U` 条件。

这不是严格的因果识别，因为 Controller 也是模型，环境可能不完全可复制；它是个人真实任务上的条件对照。

### C.2 能力边界的四个来源

1. **原始用户消息**：明确目标、事实、偏好和约束；
2. **用户历史动作**：纠正、批准、拒绝、要求验证的行为；
3. **任务环境**：用户能看到什么、拥有哪些权限；
4. **运行中获得的信息**：当前 Agent 产生的结果和错误。

第四类信息只能在候选运行已经产生相应证据后使用。Controller 不应把原 Agent 后来发现的答案回填成用户一开始就知道的事实。

### C.3 为什么不直接复刻原用户行为

原用户在历史运行中可能：

- 忘记提供某个约束；
- 因为当时的 Agent 行为而提出了特定反馈；
- 做出偶然的低质量决定；
- 看到结果后才改变需求。

直接 replay 会把这些偶然性固化为测试条件，既不能帮助候选模型自然完成，也不能表达“同一个用户面对另一条轨迹会怎样协作”。

## D. Controller 行为的判定边界

### D.1 `continue`

触发条件：Agent 已到输入边界、没有需要纠正或补充的事项，继续执行仍然有价值。

典型消息：

- “继续”；
- “接着做”；
- “按这个方案继续”；
- “可以，直接落地”。

`continue` 不表示 Controller 认为任务完成，也不表示 Agent 仍在运行。

### D.2 `inform`

触发条件：用户已经知道某个事实、偏好或约束，但候选 Agent 当前缺少它。

典型消息：

- “目标是兼容 Node 18，不要升级公共 API。”
- “这个页面主要在手机上使用。”
- “保留现有文件格式，不要迁移数据。”

如果 Agent 已经理解该事实，就不应重复补充。

### D.3 `correct`

触发条件：当前目标理解、计划或产物已经和用户意图出现可识别偏差。

典型消息：

- “我不是要重写整个页面，只修复筛选状态丢失。”
- “不要扩大范围，先解决测试失败。”

纠正应尽量指出偏差和边界，不替 Agent 写完整实现方案。

### D.4 `verify`

触发条件：Agent 声称完成、改动风险较高，或产物存在但缺少影响验收的证据。

典型消息：

- “请运行相关测试，并说明覆盖了哪些场景。”
- “请展示最终页面效果。”
- “列出实际改动并确认没有影响公共接口。”

`verify` 不是 Controller 自己运行检查；它要求 Target Agent 建立证据。

### D.5 停止和真实用户决定

如果低风险且可逆，可以把选择委托给 Agent；如果涉及发布、删除、付款、数据迁移或权限扩大，而原始会话没有用户偏好，Controller 不能伪造授权。停止是比猜测更真实的用户行为。

## E. 观察工具的理论边界

### E.1 为什么必须提供只读观察

只看 Agent 自述会有三个偏差：

- Agent 会汇报不等于产物正确；
- Agent 不提到的错误无法被发现；
- `verify` 失去真实依据。

所以 Controller 应看到用户正常会看的 diff、截图、文件和已有输出。

### E.2 为什么不能提供任意只读 shell

“只读”不代表无副作用。命令可能访问网络、触发缓存、启动服务或完成本应由 Agent 做的诊断。任意 shell 还会造成两个执行 Agent 合并，报告无法区分贡献来源。

推荐固定声明式 adapter：每个 adapter 有输入来源、采集时机、是否可能改变状态、版本和证据引用。

## F. 证据、信任与报告

用户对 Agent 通常是部分信任：愿意放权，但会检查高影响操作和完成声明。报告必须区分：

- Agent 自述；
- Agent 已执行的检查；
- Harness 的被动观察；
- 报告阶段独立验证。

这些证据不能混成一个“成功”标签。报告应以时间线和可回到原始 trace 的证据为中心，主观质量由用户判断。

## G. 理论上的已知限制

- Controller 不是实际用户本人，存在模型偏差；
- 完整会话可能混合用户原有知识和执行后新知识；
- 外部世界变化会破坏起点一致性；
- 一两个任务适合个人选择，不适合公共排行；
- 观察和验证本身可能改变环境，需要分开记录。

因此本项目不是标准 benchmark，也不是严格因果实验，而是带有过程记录和证据约束的个人化产品实验。
