# Reprise 开发现状评估与后续完善建议

> 评估日期：2026-08-17  
> 参考材料：`C:\dsh\DeepSeek-Harness-Coding-Agent工程实践研究.md`  
> 评估对象：Reprise 当前 `HEAD` 与本地工作区；本报告只做静态分析，不把历史验证记录等同于本次重新验证。

## 1. 执行摘要

Reprise 已经不是“只有功能代码、依赖对话维持秩序”的早期项目。它已经具备 DSH 研究中最有价值的一组工程骨架：分层 `AGENTS.md`、权威架构文档、Decision Records、文档预算与链接检查、生成内容 freshness、真实入口测试、负向门禁自检、跨平台 CI、TUI 字节级审计、覆盖率棘轮、`knip` 与 `jscpd` 熵控制，以及显式 opt-in 的真实 Runtime smoke。

按 DSH 的成熟度模型，Reprise 的**工程机制处于 L3“证据驱动”，局部已经进入 L4“自我维护”**。对于一个提交历史只有 14 个 commit、生产 TypeScript 约 1.56 万行的项目，这个起点很高。

当前最主要的问题不是“还缺更多规则或更多 gate”，而是三件更基础的事：

1. **变更面失控。** 当前工作区约有 163 个状态项；已跟踪 diff 涉及 131 个文件、约 2,029 行新增和 2,270 行删除，另有 23 个未跟踪文件。单次集成批次过大，已经削弱了 review、回退、定位和文档可信度。
2. **项目状态叙述与工作区事实不完全一致。** [`progress/MASTER.md`](../progress/MASTER.md) 写着“无待开发项”，但工作区仍存在大批未提交实现、删除、帧基线和决策记录；其中验证表还出现了字面量 `` `r`n ``。这说明 progress 文档开始承担过多流水账，并发生了自身漂移。
3. **产品效果证据落后于工程治理成熟度。** 确定性门禁已经很强，但 Recovery 的真实样本评估仍被模型连接 HTTP 401 阻塞。当前最值得投入的是验证“真实恢复是否有用、报告是否可信、隔离是否成立”，而不是继续增加 TUI 表面能力或治理资产。

因此，下一阶段应遵循一个收口原则：**先缩小批次、闭合真实效果证据，再增加功能；先删除和归档，再新增规则。**

## 4. 已经做对的部分

### 4.1 短常驻规则与路径级 delta 已经成立

根 [`AGENTS.md`](../../AGENTS.md) 只保留全局不变量，例如测试读取 `dist/`、Schema 校验边界、状态机入口、模型输入可重放、真实调用 opt-in 和 Windows 优先。[`src/AGENTS.md`](../../src/AGENTS.md) 只补依赖方向、Pack 契约、TUI 投影和原子写；[`docs/AGENTS.md`](../AGENTS.md) 只补文档归宿、唯一事实源和受控边界。

这比把所有规则堆进一个长 prompt 更可靠，也符合 DSH 的“渐进式上下文披露”。现阶段不需要继续增加更多子树 `AGENTS.md`，除非同类错误在某个子树重复出现，或该子树确实拥有独立命令和安全边界。

### 4.2 架构所有权清晰，且关键边界已经进入代码

[`architecture/overview.md`](../architecture/overview.md) 把 Harness、Product Pack、Target Runtime、CandidateRun、RunAttempt、RunManifest、EnvironmentBaseline 和 BaselineEvidence 分开；[`product-plugin-compatibility.md`](../architecture/product-plugin-compatibility.md) 规定产品私有协议只能留在 Pack 内；[`runtime.ts`](../../src/core/runtime.ts) 和 [`contract.ts`](../../src/products/contract.ts) 分别承担 Runtime 与 Product Pack 的公共端口。

同时，Schema、状态机、事件日志、原子写和 TUI 只读投影并非只写在文档里，而是由明确模块承载。这说明项目已经从“描述架构”进入“让架构成为可检查边界”。

### 4.3 验证体系能证伪，而不只是证明干净树退出 0

[`run-gates.mjs`](../../scripts/run-gates.mjs) 当前编排 build、typecheck、lint、文档、测试、CLI、TUI 帧、TUI 分析、生成文档、`knip` 和 `jscpd`。[`verify-docs.mjs`](../../scripts/verify-docs.mjs) 不只检查链接、目录模型、Decision 格式和预算，还用四类坏输入做自检；新增或修改门禁必须附反向用例的决定也已经进入 [`2026-08-15-gate-reverse-tests.md`](../decisions/accepted/2026-08-15-gate-reverse-tests.md)。

这是 Reprise 最接近 DSH 的地方：门禁不是装饰，而是必须证明自己会拒绝错误。

### 4.4 CI 已按风险分层，而不是简单复制本地全套

[`.github/workflows/check.yml`](../../.github/workflows/check.yml) 把 static、test、audit 和 coverage 分开；测试覆盖 Windows 与 Ubuntu，TUI 字节基线只在 Windows 审计。这既尊重 Windows 11 的产品基线，也保留跨平台代码健康检查。

这种分层比“每次本地都跑所有昂贵检查”更合理。下一步应优化可观测性，而不是再增加 lane 数量。

### 4.5 项目主动控制熵

项目已经使用 `knip` 查未使用导出、用 `jscpd` 限制重复、用覆盖率棘轮禁止阈值倒退，并在当前变更中删除旧 Report renderer 主路径。这符合 Ponytail 与 DSH 的共同原则：先删重复表示和无消费者抽象，再考虑增加框架。

## 5. 当前最需要解决的问题

### 5.1 P0：当前开发批次过大，已经成为首要工程风险

当前已跟踪 diff 横跨 131 个文件，并同时触及：

- Product Pack 会话发现与分页；
- Comparison Agent HTML 报告；
- TUI Controller、页面和 40 余份帧基线；
- Schema、存储、恢复工具；
- 门禁、CI、生成文档和文档规则；
- 多组测试和快照。

即使每个局部修改都正确，这种批次也很难回答“哪一部分导致回归”“哪个决策对应哪些代码”“能否只回退一项功能”。它还使一次 `npm run check` 的绿灯只能证明大集合整体可运行，不能证明每个变化都有清晰因果。

建议立即停止把新功能并入这一批次，先按用户可观察能力和协议耦合收口为若干可独立 review 的单元。建议顺序是：

1. 门禁与文档基础设施；
2. Comparison HTML 报告协议；
3. Product-first Intake 与 Session discovery；
4. TUI 投影与帧基线；
5. Recovery 历史辅助和凭据配置。

这不是要求机械拆成很多小 commit，而是要求每个单元能独立说明：目标、非目标、关键文件、决策、受影响测试和回退边界。当前批次未收口前，不应继续增加第三个 Pack、更多 TUI 页面或新的治理 gate。

### 5.2 P0：Progress 记录需要从“流水账”恢复为当前状态索引

[`progress/MASTER.md`](../progress/MASTER.md) 同时保存目标、完成项、决策摘要、十余条验证历史和风险，已经出现三个信号：

- “无待开发项”与大量工作区变更并存；
- 多个已实施计划仍留在 `docs/plan/`；
- 验证表中出现了字面量 `` `r`n ``，说明生成或编辑过程没有被文档 gate 识别为语义错误。

建议把 MASTER 限制为一屏内的当前状态：当前目标、范围、当前任务、阻塞、下一动作和最近一次有效验证。历史验证只保留最近一条；其余依赖 Git、Decision Record 或本地归档。已完成的计划按 [`documentation-structure.md`](../documentation-structure.md) 的规则移出受控 `plan/`，不要继续通过状态前缀把完成文档留在活跃计划区。

同时应给 progress 增加一个非常小的语义检查，而不是复杂 schema：至少拒绝字面量换行转义、要求 Current Objective 与 Next Actions 不互相矛盾、只允许一条“最近全门禁”记录。只有这类漂移再次出现时再把检查升级为正式 gate。

### 5.3 P0：真实恢复效果是当前最大的产品证据缺口

[`recovery-module-real-sample-evaluation.md`](../plan/recovery-module-real-sample-evaluation.md) 已经设计了 Codex 与 Claude Code 各 5 条真实历史样本的评估，但模型连接预检收到 HTTP 401。在预检通过前，继续优化 Recovery prompt、恢复报告样式或 TUI 展示都无法回答最重要的问题：恢复后的隔离工作区是否真的足以继续原任务。

建议把解除 401 和完成 10 条样本评估设为下一阶段唯一产品 P0。完成标准不是“脚本运行成功”，而是：

- 原始历史目录与源工作区指纹不变；
- staging 隔离成立；
- 每条样本先独立审查实际文件系统，再阅读 `recovery.md`；
- 结果区分有效恢复、基本可用、表面恢复、错误恢复和证据不足；
- 报告只保存脱敏摘要，不保存完整 transcript、密钥或敏感绝对路径；
- 失败样本能够归因到导入、证据不足、Recovery 判断、环境复制或 Runtime 调用中的具体一层。

这项工作完成后，才有足够证据决定 Recovery 应该改 prompt、改工具、改证据模型，还是保持现状。

### 5.4 P1：治理很强，但尚未度量治理成本

当前 11 个本地 gate 已覆盖主要风险，但没有看到 gate 的 p50/p95、失败命中率、误报率或常见失败归因。随着仓库增长，治理资产可能像代码一样产生维护税。

建议让 [`run-gates.mjs`](../../scripts/run-gates.mjs) 在现有汇总上附加每个 gate 的耗时，并可选写入 Git 忽略的本地 JSON。先观察 2–4 周，不建立数据库、不引入依赖、不上传遥测。每月只回答四个问题：

1. 哪个 gate 最慢？
2. 哪个 gate 真正拦住过缺陷？
3. 哪个 gate 经常因环境波动失败？
4. 哪些检查重复覆盖同一风险？

长期零命中、成本高且被其他检查覆盖的 gate 应合并或删除。L4 的关键不是 gate 多，而是 gate 可回收。

### 5.5 P1：核心 Controller 已超过项目自己的文件体积边界

[`src/tui/controller.ts`](../../src/tui/controller.ts) 约 1,164 行，已经超过当前工程规则的 1,000 行上限；[`experiment.ts`](../../src/application/experiment.ts) 约 843 行，也接近需要重点观察的体积。Controller 同时参与输入、运行、发现结果、页面切换和状态投影，后续继续加功能会扩大耦合。

不建议进行“按类名拆文件”的形式化重构。应沿现有真实 seam 做最小抽取：

- 会话发现请求、取消、晚到结果隔离；
- Intake 选择状态与分页；
- Candidate run 生命周期协调；
- 纯页面导航状态。

每次只抽一个已有职责，保留 Controller 为组合入口，并用现有 focused tests 证明行为不变。若抽取后没有多个调用方，也不要再造通用 manager、service 或 event bus。

### 5.6 P1：计划与决策的生命周期需要真正执行

项目已经有 `accepted`、`proposed`、`superseded` 三个决策目录，这是好的基础。但 `docs/plan/` 中仍可见多个“已实施”计划，说明“文档放置规则”已经建立，生命周期执行还不稳定。

建议每次大任务结束时只做一次收口：

- 已长期约束实现的选择进入 accepted Decision；
- 当前实现规则回写 architecture/product；
- 完成计划移入 Git 忽略的 `docs/.local/archive/`；
- MASTER 只指向下一个活跃计划；
- 被新决策替代的记录进入 superseded，并双向链接。

不要引入 DSH 规模的 Agent Notes 双语配对、hash sealing 或几十项 note gate。以 Reprise 当前规模，Decision + 短 MASTER 已足够。

### 5.7 P2：测试数量充足，但应继续区分“协议正确”和“产品有用”

当前测试覆盖 Pack、Experiment、Store、TUI、快照、污染、恢复工具和 CLI，历史记录显示已有 300 余个测试。下一步不应以增加测试数量为目标，而应优先补三类证据：

1. **真实入口 assembled snapshot**：验证模型实际收到的 system prompt、工具描述、事件投影和报告输入，而不是分别测试字符串片段。
2. **失败路径的负向控制**：只针对曾发生或高风险的凭据泄漏、源目录污染、状态非法跳转、晚到 discovery 覆盖和损坏 JSON 持久化。
3. **效果评估**：真实恢复质量、Comparison 报告是否引用了可追溯事实、用户是否能从报告做出判断。

覆盖率继续作为底线，不应为了覆盖未使用分支而保留死代码，也不应为了提高数字复制低价值测试。

## 6. 建议的后续开发路线

### 6.1 未来 0–14 天：停止扩张，完成当前批次收口

**目标：把当前工作区恢复成可审查、可回退、状态叙述一致的基线。**

1. 冻结新功能，只处理当前 131 文件 diff 内的收口问题。
2. 按能力边界审阅 diff，确认每个删除文件都有替代入口，每个新增协议都有 owning Decision。
3. 清理 MASTER 的字面量转义和重复验证历史。
4. 把已实施计划移出活跃 `plan/`，保留唯一活跃计划。
5. 对每个收口单元运行一次直接受影响测试；源码最终稳定后只运行一次 `npm run check`。
6. 记录当前全门禁的真实结果，不沿用修改前的历史绿灯。

**Done-means：**工作区中的每个能力变更都能映射到一个目标与验证；MASTER 与实际状态一致；最终 `npm run check` 通过；没有为绿灯放宽覆盖率、重复阈值或 allow-failure。

### 6.2 未来 15–30 天：完成真实 Recovery 证据闭环

**目标：回答“Reprise 能否诚实且安全地恢复真实任务”。**

1. 只修复本机 Harness 模型 endpoint / API key 配置导致的 401，不读取 Codex 凭据，不把密钥写入事件或报告。
2. 先运行最小连接预检，失败即停止，不提前 freeze 或复制历史数据。
3. 按现有计划执行 Codex 5 条、Claude Code 5 条分层随机样本。
4. 汇总失败分类，优先修共享根因；不要为单一样本在应用层增加产品特判。
5. 只有发现重复失败模式时，才把它升级为 defensive rule、回归测试或架构约束。

**Done-means：**10 条样本均有机械隔离证据和独立语义结论；阻塞与产品失败分开记录；没有敏感数据进入受控 Git 文档。

### 6.3 未来 31–60 天：用真实使用反馈收敛产品，而不是扩展框架

**目标：确认最短用户闭环稳定。**

建议固定唯一主路径：

```text
/config → /intake → /run → /history → report.html
```

围绕这条路径完成：

- 首次配置失败、取消、重试和退出体验；
- 两个 Pack 的身份、会话隔离和 Runtime 事实一致性；
- 运行中断与崩溃后的可解释状态；
- Comparison 报告中事实到事件的可追溯性；
- 一次全新目录安装、运行和卸载数据保留策略演练。

这阶段不要建设插件市场、动态 Pack 加载、分布式执行、通用 PTY、远程服务或多用户权限系统。现有静态双 Pack 足以暴露公共契约问题。

### 6.4 未来 61–90 天：建立轻量自我维护循环

**目标：让规则、文档和 gate 可以被删除，而不是只增长。**

1. 为 gate 增加耗时观测，形成本地 p50/p95。
2. 每月做一次 30 分钟治理审计：过期计划、重复事实、无 consumer 导出、低价值 gate。
3. 从真实 Recovery 或 Runtime 事故中选择一项，提炼为最小 defensive pattern；没有真实事故就不创建新文档。
4. 对 `controller.ts` 做一次沿职责 seam 的小型拆分，停止其继续增长。
5. 决定是否需要第三个 Product Pack：只有当真实用户需求无法由 Codex/Claude Code 覆盖，且第三个 Pack 能验证公共契约时才做。

**Done-means：**至少删除或合并一项低价值治理资产；gate 时间可见；活跃 plan 数量保持很小；Controller 回到体积边界内且行为测试不变。

## 8. 建议跟踪的最小指标

不要统计 AI 生成代码行数。建议只记录下面 8 项，并且先用 Git 忽略的本地 JSON 或每月人工表格，不建设新系统：

| 维度 | 指标 | 目的 |
|---|---|---|
| 范围 | 每个任务涉及文件数、最大单批 diff | 防止再次出现百文件批次 |
| 交付 | 从明确目标到全门禁通过的时间 | 识别流程阻塞 |
| 返工 | 同类 review finding 的复发次数 | 判断规则是否有效 |
| 稳定 | 失败回滚、flaky gate、escaped defect | 不被测试数量误导 |
| 证据 | 真实入口测试数、带负向控制的高风险修复比例 | 检查是否可证伪 |
| 产品 | Recovery 样本分类、报告事实可追溯率 | 衡量实际效用 |
| 反馈 | 各 gate p50/p95、失败命中率 | 删除低价值治理 |
| 上下文 | 根/子树 `AGENTS.md` 字符数与重复规则数 | 保持注意力预算 |

建议设置一个简单预警而非硬门禁：普通任务超过 20 个文件时必须解释为什么不能拆；超过 50 个文件默认先停止扩张并重新划分能力边界。这个阈值用于触发审查，不应机械阻止必要的生成文件或帧基线更新。

## 9. 最终建议

Reprise 当前最稀缺的不是代码生成能力，而是**小批次交付纪律和真实产品效果证据**。工程治理已经明显领先于项目规模，继续增加规则的边际收益很低；相反，收口当前工作区、清理状态文档、完成真实 Recovery 样本、测量 gate 成本，会直接提升可信度。

后续每个非平凡任务都应能回答四个问题：

1. 本次唯一目标和明确非目标是什么？
2. 哪个架构/产品文档拥有这条事实？
3. 哪个真实入口或负向控制能够推翻“已经完成”的自述？
4. 新增的代码、文档或 gate 在什么条件下可以删除？

如果未来 90 天只完成三件事，优先顺序应是：

1. 把当前大工作区收口成可审查基线；
2. 完成 Codex/Claude Code 真实 Recovery 样本评估；
3. 建立 gate 成本和文档生命周期的轻量回收机制。

做到这三点后，Reprise 才算从“拥有成熟工程机制”进一步走向“这些机制持续服务于真实产品结果”。
