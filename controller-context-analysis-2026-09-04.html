Turn 0历史理解产物应写什么

controller-task-understanding.md 不是流水账，而是结构化但可读的“语义账本”：初始目标、后续明确动作、交付格式变化、持续约束、验收信号、用户表达风格、当前未完成事项。

必须附 transcript message id 和文件路径，便于复核“这条判断来自哪里”。

Turn 1第一条用户输入怎么产生

Controller 读取任务画像、初始输入、当前 project 和 replay 路径，判断候选从哪里开始最自然，再以原用户口吻写第一条消息。它不是把初始句机械复制，也不是提前发送后续要求。

每轮反馈后先更新理解

每个候选回合结束后，Controller 先把新事实写入画像的“当前进度/已满足/未满足/新证据”区，再决定是否需要一条用户消息。这样最近一轮的局部修改不会覆盖早期的格式变更。

完成只在画像覆盖清零后结束

done/satisfied 的前提不是“当前文件看起来不错”，而是画像中的所有仍适用明确动作都有真实文件或检查证据；若无法验证，应 send/verify 或明确 blocked。

三、任务画像 MD 的建议结构

区块内容用途
## Task初始目标、用户希望交付的对象、允许的工作范围。定义问题边界，避免只盯住最近产物。
## Explicit actions逐条列出用户明确要求：动作、对象、格式、状态（未满足/已满足/待验证）。防止“不要机械重放”变成“忽略后续动作”。
## Constraints白底、统一风格、数据源标注、路径可见等持续约束。把修订意见与最终交付区分开。
## Collaboration profile用户如何提出修改、对视觉/证据/路径的敏感度、何时继续追问。帮助 Agent 模拟“这个人下一步会怎么说”。
## Current coverage当前文件、changed paths、可打开/渲染结果、每条动作的证据 ref。为每轮 send/done 提供可审计依据。
## Decision log每轮为什么发这句话、解决了什么未满足项、下一轮要重新检查什么。压缩后恢复推理链，避免只剩最后一次局部总结。
关键边界：Host 可以创建文件、保存版本、校验路径和记录证据，但不能替 Agent 填写“PPT 是下一步”这样的语义结论。画像由 Controller 生成，Host 只保证它可恢复、可追溯、不会被候选看到。

四、按你的思路重排后的运行序列

认知回合：理解历史，不发送

读取完整 transcript，重点扫描用户消息；识别目标变化、格式变化、约束、验收标准和用户协作节奏。写入初始任务画像，并在 audit 中记录读过哪些 message id。

开场回合：从画像生成第一条输入

读取画像与当前工作区，选择符合原始起点的最小自然请求。此回合只负责产生第一条 user message，不能把后续历史句按顺序倾倒给候选。

反馈回合：先更新画像，再输出下一条

候选 turn settled 后，读取 THIS-TURN、project 和当前画像；把新事实合并到覆盖清单。若存在未满足的明确要求，生成一条针对当前状态的自然反馈；如果要求已满足，才考虑 done。

恢复/压缩：恢复画像，不依赖自由摘要

发生 session compact、进程恢复或重建 session 时，优先读取持久化画像 MD。早期目标、格式变化、未满足动作和证据路径必须是保留字段。

五、落地前必须解决的能力边界

当前 Controller 不能直接按普通文件写入画像。现有 system prompt 说明 edit 和 write 已注册，但写入被拒绝；因此“让 Agent 写一个 MD”如果直接依赖现有工具会失败。推荐让 Agent 在一次认知调用中返回受约束的画像正文，由 Host 校验后写入 run-owned briefing，或提供只允许写入该目录的专用 save_controller_understanding 能力。

推荐接口：语义输出，Host 持久化

认知调用返回 understanding_markdown、sourceMessageIds、openQuestions，Host 通过 schema 校验后写入 controller-task-understanding.md。这仍由 Agent 负责理解，Host 只负责保存和追溯。

不推荐接口：开放式写文件

给 Controller 全部写权限会扩大边界，可能污染候选目录或把模型推理写到错误位置。画像必须位于 Host-owned、candidate 不可见、run-scoped 的目录，并保留版本。

八、System prompt 的具体问题

P1历史定位过度偏向“习惯”

“History is for whether this user would stop or steer, not a queue to send in order.” 本意是防止剧本式重放，但没有同时规定：后续用户句中的明确动作、格式变更、交付对象仍然是有效任务事实。

副作用：模型更容易观察“用户会不会继续挑剔 HTML”，而不是确认“PPT 是否已经生成”。

P1完成判断没有覆盖检查

“Would this user ... actually stop here?” 没有要求列出所有仍适用的明确要求，再逐项用当前文件证明。于是“HTML 看起来合格”被误当成“全局任务完成”。

P2注意力锚定当前回合

steering 先读 THIS-TURN 和 project，历史只在必要时再读。这个优先级适合降低成本，却会让最近的 HTML 局部修改压过较早但更高优先级的格式要求。

P2Host 只做 schema 校验

Host 会校验 decision 结构和 evidence ref，但不会拒绝“没有 PPT 却 done”。这是正确的边界方向，却缺少对 Agent 的强制推理契约和评测反向用例。

九、上下文管理：本次事实与未来风险

本次不是压缩问题

事件统计中 Controller 的 agent.context_compacted 为 0；四次调用共享同一 session，但没有发生 summary + retained tail 替换。因此不能说 PPT 要求被 compact 丢失。

设计仍有两个风险

一是每轮正文很短，历史要靠工具主动发现；二是未来长会话发生压缩后，模型生成的 summary 可能保留“当前进展”而弱化早期格式变化。压缩摘要不应成为唯一记忆来源。

当前结构的可观测缺口

SteeringContext.task.historicalUserTurns 在实际构造中为空，虽然 transcript 文件存在；controllerRequestSnapshot 也不记录 Agent 已读取哪些历史句，只记录路径和摘要。

应保留的边界

不把“HTML 后必须 PPT”写入 Host；不要求发送次数等于历史用户句数；不让 Host 替 Agent 做产品语义判断。Host 只提供事实、持久化、权限和生命周期。

十、Agent-first 方案对比

A. 只改 prompt

新增“读取所有后续用户消息；提取动作/对象/格式/约束；与当前产物逐项对照；有未满足项不得 done”。

成本低，最贴近现有设计；依赖模型持续执行检查。

B. Prompt + 语义中立账本 推荐

Host 每轮生成不可伪造的事实索引：历史用户句、候选文件、扩展名、渲染/打开结果、已发送消息。Agent 自己判断哪些要求仍有效、下一步怎么说。

改善可见性和可审计性，但不硬编码 HTML/PPT 流程。

C. 每轮完整 transcript 注入

把全部历史正文直接放入每次 request，减少工具读取。

最直观但 token 成本高、重复多，且仍不能保证模型做语义对照；只适合短会话或诊断模式。

十一、推荐的新契约

Controller 每次 steering 必须先完成三步内部工作：（1）读完整用户后续消息，提取仍可能有效的明确动作与约束；（2）检查当前回合和 workspace 的真实文件，尤其是用户点名的格式和路径；（3）形成“已满足 / 未满足 / 无法验证”清单。只有不存在未满足的明确动作，才可返回 done/satisfied。
# Reading the historical session
The full transcript is evidence of this person's goals and task changes, not a script.
Do not replay sentences mechanically. Do extract every still-applicable explicit
action, deliverable format, named object, constraint, and verification request.

# Before done/satisfied
Read the relevant later user messages and current project files. Compare each
explicit requirement with an observable artifact or check. A polished artifact
of the wrong format is not complete. If any explicit action is unmet or unverified,
send the shortest natural follow-up in this user's voice. Explain the coverage
in rationale/evidenceRefs, but do not leak analysis into the user message.

十二、生命周期与结果可审阅性

独立系统缺陷：副本释放

run 结束事件记录了 environment.release_completed。候选 HTML 曾在隔离副本中，但副本释放后用户找不到它。这与 Controller 是否正确判断是两条独立故障链。

应成为交付不变量

停止 Runtime 不等于删除审阅材料。结束时应把候选文件复制到 experiment-owned deliverables，保留 workspace 直到用户显式清理，并在结果页显示完整绝对路径。

十三、验证与提分顺序

优先级动作通过标准
1马上改 prompt 与 request briefing，加入“要求—产物覆盖检查”。fixture 中 HTML 已有但 PPT 未有时，Controller 必须 send；PPT 和 HTML 都有且可验证时才可 done。
2随后增加语义中立的历史/产物事实索引和读取审计。报告能显示每条用户动作被读到、被采用或被判定已满足。
3随后固定压缩摘要的保留字段：早期目标、后续格式变化、未满足动作、当前文件。发生 compact 后仍能恢复同一覆盖清单；不能仅依赖模型自由摘要。
4交付保存 deliverables、保留 workspace、结果页打印路径。run 结束后 HTML/PPT/截图可打开；未生成项明确显示“未生成”。
最终责任判断：本次流程判断错误的直接责任在 Controller Agent；根因是历史语义整合和完成覆盖检查不足。候选模型是次要因素，副本释放是独立的交付生命周期缺陷。推荐以方案 B 为主，保持 Agent 判断任务流程，Host 只提供可验证事实和可持续交付物。
